## 지금 파는 중

*(덮어쓴다. 이어붙이지 않는다.)*

**Grab — 30번째 회사, 동남아 첫 회사.** 사이클 170 에서 열었다. 프로파일 + 도메인 2개 +
기능 1개(`counter-service`). **`SG` 를 validate.py COUNTRIES 와 index.json countries 에 추가했다.**

> **다음 기능은 `데이터 레이크`** — Iceberg 이관 글은 이미 읽었다(HMS 가 **중앙 장애점 + O(n)
> 목록 조회**, ML 데이터셋 **평균 1MB 미만·파티션당 수천 개**, **카탈로그와 저장소가 어긋남** /
> 질의 **70초→6초**, S3 API 비용 **95% 절감** / `TIMESTAMP_NTZ`↔`TIMESTAMP_LTZ` 충돌, HMS **좀비 락**).
> **두 번째 글이 필요하다** — `real-time-data-ingestion`·`migrating-existing-datastores` 를 볼 것.
> ⚠️ **배차 자료는 아직 확인 안 했다** — 카카오·배민·우버와 겹칠 수 있으니 자료를 보고 판단.

> **`counter-service` 에서 나온 것 — 인덱스는 데이터가 아니라 개수에 비례한다.**
> 주 인덱스가 **레코드당 64바이트·메모리 상주**라, 수십억 카운터에서는 **데이터가 SSD 에 잘
> 들어가 있어도 인덱스가 먼저 RAM 을 다 쓴다.** 그래서 버킷마다 행을 만드는 두 안이 **조회
> 방식만 다를 뿐 같은 벽**에 부딪혔다 — **레코드 수가 그대로였기 때문**(해석). 답은 **한 레코드
> 안의 맵으로 접는 것**(저장 3TB→약 1TB, 읽기 p99 약 50% 개선, 노드 비용 45~50% 절감).

> **🔗 드문 기록 — 해 보고 되돌렸다.** 인덱스를 **로컬 NVMe 로 내렸다가 되돌렸다.** 계산은
> 합리적이었다(추가 지연이 요청 예산 안에서 안 보일 것). 그런데 **p99 스파이크가 전체 QPS 가
> 아니라 핫 키의 I/O 를 따라갔고**, 노드를 더 붙여도 **약간만** 나아졌다 — **부하의 총량이 아니라
> 쏠림**이 문제였다(해석). 회사의 문장: *"같은 레코드에 동시 조회가 몰릴 때 인메모리 인덱스가
> 디스크 기반보다 더 신중하게 다룬다."* **비교 문서 `안 하기로 한 것을 어떻게 적는가` 의 축과
> 가깝지만 결이 다르다** — 저쪽은 '안 켰다', 이쪽은 **'해 보고 되돌렸다'**.
> **⑫ 새 축 후보: '해 보고 되돌린 것'** — Cloudflare `workers-kv-redundancy`(이미 쓰임) ·
> Zalando AZ 친화(이미 쓰임) · **Grab NVMe 인덱스** · 확인 필요한 것들. **재료 확인할 것.**

> **⚠️ 미사용 기능이 줄고 있다** — 사이클 169 에서 7개를 썼다. 다음 비교 문서 전에 **남은 개수부터
> 확인**하고, 얇으면 회사를 더 파는 쪽을 먼저 고를 것.

> **큐를 못 채웠다 (1/3, trivago 하나).** 이번엔 회사 프로파일과 기능에 시간을 썼다.

> (열린 곳: canva.dev · engineering.zalando.com · tech.trivago.com · grafana.com · adyen.com ·

  Shopify 판매 단위당 1행 / 토스 계좌 락 / Discord 요청 병합 / Stripe 멱등 키.
