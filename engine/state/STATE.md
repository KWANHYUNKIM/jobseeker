## 지금 파는 중

*(덮어쓴다. 이어붙이지 않는다.)*

**Dropbox — 진행 중. 21번째 회사다.** 도메인 4개 중 **3개 완료** — 저장 인프라(`magic-pocket`),
파일 동기화(`nucleus-rewrite`), 전송 효율(`compression`). 남은 것: **검색** 하나.
Nautilus 글이 자리다(세 겹째 자료가 필요하면 Firefly 대체 판단 글을 함께 볼 것).

> **이 회사를 고른 이유 = 원가가 남의 클라우드가 아니라 자기 하드웨어에 있다.**
> 앞의 20곳은 전부 남의 클라우드 위에 있었다. Dropbox 는 2013년 여름에 시작해 2016년에
> 500PB 를 S3 에서 자기 인프라로 옮겼고, **그 결정이 지금도 손익계산서에 잡힌다** —
> FY2025 GAAP 매출총이익률이 82.5% → 80.1% 로 내렸고 회사가 원인을 **'데이터센터
> 갱신 주기'의 감가상각**이라고 명시했다. 기술 결정이 재무제표에 보이는 드문 경우다.

> **136 에서 확인됐다 — 자료를 네 겹으로 겹치니 글 하나의 구멍이 메워졌다.**
> Cowling(버린 대안) + Gupta(일정·숫자) + SSD 제거 글(2022, 대가까지) +
> InfoQ/Agriel(2023, 소거 부호·콜드 계층 수치). **회사 블로그만으로는 RS(6+3)·LRC·1.33배도,
> 콜드 XOR 2배→1.5배도 안 나왔다** — InfoQ 글이 드롭박스 엔지니어가 쓴 것이라 1차에 준한다.

> **자료 성격이 글마다 다르다 — 중요하다.**
> `Inside the Magic Pocket`(2016-05, James Cowling)은 **버린 대안을 제대로 적었다** —
> 쿼럼 프로토콜·DHT·Paxos·자체 KV 를 전부 버리고 **샤딩된 MySQL** 을 골랐고, 이유가
> '복잡함은 대개 신뢰성의 반대다'와 '엔지니어 여섯 명도 안 됐다'였다.
> 반면 `Scaling to exabytes`(2016-03, Akhil Gupta)는 **성공만 적고 대가를 안 적는다.**
> → 저장 인프라 기능은 **Cowling 글을 축으로** 삼고 Gupta 글은 일정·숫자로만 쓸 것.

> **작업 메모:** `dropbox.tech` 는 WebFetch 로 잘 읽힌다. ⚠️ **기사 URL 을 추측하지 말 것** —
> `scaling-to-exabytes-and-beyond` 는 404 이고 실제 주소는 `magic-pocket-infrastructure` 다.
> 검색으로 실제 주소를 확인하고 들어갈 것. Broccoli 글 주소는 하이픈이 특이하다
> (`/-broccoli--syncing-faster-by-syncing-less`).

> **비교 재료 셋.** ① **'사고 vs 짓고'** — Dropbox 는 떠났고 나머지 20곳은 남았다.
>   Cloudflare 는 아예 인프라가 제품이라 축이 또 다르다.
> ② **'리팩터링으로는 데이터 모델을 못 바꾼다'** — Nucleus 4년 재작성 / Slack Vitess 3년 /
>   Notion 블록 테이블. **셋 다 '전제가 데이터 모델에 박혔다'는 같은 모양이다.**
> ③ **'일부러 시시한 것을 고른다'** — Magic Pocket 이 Paxos 대신 MySQL / Slack 이
>   NoSQL 대신 MySQL 위의 Vitess. 이유도 같다 — 사내에 이미 있는 운영 지식.

**큐 3/3 — 충분.** 다음 대기는 GitHub → LY(LINE).

마지막 사이클: 138 (2026-08-21) — 압축 둘(Broccoli·Lepton).

> **비교 축 '옮기기 전에 옮김을 재는 장치'에 세 번째가 붙었다.**
> Lepton 저장 전 비트 비교 / Slack Vitess 이중 읽기 대조 / Shopify 섀도 모드.
> **셋 다 '맞을 것이다'를 믿지 않고 실제 결과를 맞대 본다**는 같은 모양이고,
> 대가도 같다 — 처리를 두 번 한다. 비교 문서로 쓸 재료가 충분해졌다.

> **Netflix 축('평균에 맞춘 하나의 답을 버린다')에 다른 경로로 도착한 사례.**
> Broccoli 절감이 평균 30% 인데 실제로는 **절반 13% · 25%가 40% · 10%가 70%** 다.
> 게다가 **회선이 빠르면 압축이 손해**라 같은 코드가 사용자에 따라 이득도 손해도 된다.

> **비교 축 '리팩터링으로는 데이터 모델을 못 바꾼다'가 여기서 가장 선명해졌다.**
> 회사가 **재작성 판단 체크리스트를 그대로 공개했다** — ① 점진적 개선을 다 써 봤는가
> ② 해낼 수 있는가(**지금 시스템을 깊이 이해하고 존중하는가** / 기능 개발이 느려지는 것을
> 받아들일 수 있는가) ③ 어디로 가는지 아는가. Slack Vitess(3년)·Notion 블록 테이블과
> 나란히 놓을 때 **이 체크리스트가 비교 문서의 뼈대가 된다.**
> 숨은 비용도 적혀 있다 — **'옛 시스템에 변경이 하나 들어갈 때마다 결승선이 그만큼 멀어졌다.'**

> **새 축 — '무작위 테스트의 설계란 어디에 무작위를 넣지 않을지를 정하는 일이다.'**
> CanopyCheck 이 세 나무를 독립 생성하면 겹치지 않는 나무만 나와 **삭제·편집·이동 로직을
> 한 줄도 안 지난다** — 그런데 테스트는 통과한다. 그래서 하나를 만들고 **교란해** 나머지를 만든다.
> Netflix·Shopify 의 '미리 한계를 찾아 둔다'와는 다른 결의 축이다.

> **새 비교 축 — '캐시를 빼는 것이 답일 때'.** Dropbox 가 2017년에 넣은 SSD 쓰기 캐시를
> 2021년에 **뗐다**(쓰기 처리량 +15~20%). 넣은 판단도 옳았고 뺀 판단도 옳았다 —
> **밀도가 오르면서 캐시가 성능을 주는 자리에서 막는 자리로 옮겨 갔다.**
> Discord '터진 뒤 끊는 대신 들어가기 전에 센다'와 방향이 반대라 같이 놓으면 좋다.

> **서술 관례 하나 굳혔다 — `stateDiagram-v2` 안에서는 `**` 를 쓰지 않는다.**
> 기존 66개 stateDiagram 중 쓴 것이 0개였다(머메이드가 그대로 뿌린다).
> 강조가 필요하면 flowchart 로 그린다 — flowchart 는 201개 중 39개가 쓴다. 136 에서 한 장 고쳤다.

### 되풀이되는 설계 축

여러 회사에서 같은 모양이 반복해서 나온 것들. 비교 문서의 씨앗이자, 새 회사를 팔 때
"여기도 같은 문제가 있나"를 먼저 물어볼 목록이다.

- **충돌을 해결하는가, 충돌이 안 생기게 만드는가** — Figma 속성 단위 LWW·분수 인덱싱 /
  Shopify 판매 단위당 1행 / 토스 계좌 락 / Discord 요청 병합 / Stripe 멱등 키.
- **몰리는 것을 한 곳에서 합친다** — Discord 요청 병합·Manifold·길드당 음성 서버 1대.
- **터진 뒤 끊는 대신 들어가기 전에 센다** — Discord Semaphore·침묵 억제.
- **격리의 단위가 곧 전환의 단위** — Shopify pod 이동·리전 페일오버·pod 단위 점진 전환.
- **분포에 맞춘 설계는 분포 밖에서 정확히 실패한다** — Slack 여러 샤드 순회가 보통
  사용자에겐 잘 돌고 수백 워크스페이스에선 무너져 50개로 자른 것 / Discord 대형 길드.
- **미리 한계를 찾아 두고 되돌릴 길을 열어 둔다** — Shopify 스케일 테스트·섀도 모드·
  Verifier·성수기 변경 동결 / 토스 카나리 자동 롤백.
