## 지금 파는 중

*(덮어쓴다. 이어붙이지 않는다.)*

**trivago — 31번째 회사.** 사이클 174 에서 열었다. 프로파일 + 도메인 2개 + 기능 1개
(`kafka-consumers`). **다음 기능은 `내부 API 통합`** — GraphQL 글은 이미 읽었고 두 번째 글로
`2022-05-16 warp-a-web-application-rewrite-project` 를 확인하면 된다.

> **이 회사의 축 — 자기 재고가 없다.** 남의 가격을 모아 비교하고 클릭에서 매출을 얻는다:
> FY2025 총매출 **5억 4,890만 유로** 중 **리퍼럴이 5억 3,290만 유로 — 약 97%**(이 사이트의 계산).
> 그래서 **가격이 낡으면 그게 곧 장애다** — lag 이 쌓이면 늦는 게 아니라 **만료된 호텔 가격이
> 하류로 나간다.** 쿠팡·아마존(자기/셀러 재고)과도, 네이버·구글(문서 색인)과도 다른 자리다.

> **`kafka-consumers` 에서 나온 것 — 하나씩 고쳐서는 아무것도 나아지지 않는다.**
> reactor-kafka 로만 바꿔도, `delayElement` 만 없애도, gRPC 스레드만 늘려도, 복제본을 더 붙여도
> **전부 효과가 없었다.** **네 곳이 동시에 막고 있었기 때문**이고, **하나를 풀면 다음 것이 즉시
> 천장이 되어 고쳤다는 증거가 안 나타난다**(해석). 넷을 함께 고치니 파드 **60 → 6**(배포 비용 83%↓),
> 기동 **60초 → 10초**, P1 중단. **사업 지표는 그대로**였다는 것도 적었다.

> **두 글이 같은 관찰을 한다 — 이 부하는 CPU·메모리에 나타나지 않는다.** 컨슈머는 부하가 높은데
> **CPU 10% 안팎**이었고, 싱크 쪽은 *"처리할 메시지가 많다는 의미에서 바쁠 수 있지만 CPU 가 꼭
> 튀지는 않는다"* 고 적는다. **이 부하가 기다림으로 이루어져 있기 때문**(해석). 답은 **밀린 양
> 자체(lag)를 신호로** 삼는 것 — KEDA 로 0까지 축소해 리전당 하루 **50 → 1~2 replica-hours**.
> 🔗 **이건 비교 문서 `잘못된 자를 어떻게 알아채는가` 의 축과 정확히 같다** — 그 문서에 이미
> 다섯 사례가 있으니 **넣을지는 판단할 것.** ⑨ '같이 몰린다'와도 다른 결이다.

> **새로 보인 것 — 신호가 신호원에 의존한다.** lag 을 신호로 삼으면 **저트래픽 토픽은 2주 뒤
> Kafka 가 소비자 그룹 메타데이터를 지워 lag 자체가 사라진다** → Cron 으로 깨워 둬야 한다.
> 메트릭을 6회 연속 못 가져오면 1개로 폴백한다. **⑭ 새 축 후보: '신호가 사라지는 자리'**(재료 확인).

**큐 잔량 1/3 — 목표 미달.** Allegro 하나. **다음 사이클에 후보를 하나 올릴 것** —
자체 도메인 + 정적 블로그가 열릴 확률이 높다. 🚫 Medium·Delivery Hero·Zomato/Swiggy·Nubank 는 막혔다.
