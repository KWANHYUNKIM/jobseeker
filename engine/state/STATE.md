## 지금 파는 중

*(덮어쓴다. 이어붙이지 않는다.)*

**Dropbox — 진행 중. 21번째 회사다.** 프로파일(3단계)까지 했다. 도메인 4개 전부 비었다:
**저장 인프라** · 파일 동기화 · 전송 효율 · 검색. 사다리가 저장 인프라를 먼저 가리킨다.

> **이 회사를 고른 이유 = 원가가 남의 클라우드가 아니라 자기 하드웨어에 있다.**
> 앞의 20곳은 전부 남의 클라우드 위에 있었다. Dropbox 는 2013년 여름에 시작해 2016년에
> 500PB 를 S3 에서 자기 인프라로 옮겼고, **그 결정이 지금도 손익계산서에 잡힌다** —
> FY2025 GAAP 매출총이익률이 82.5% → 80.1% 로 내렸고 회사가 원인을 **'데이터센터
> 갱신 주기'의 감가상각**이라고 명시했다. 기술 결정이 재무제표에 보이는 드문 경우다.

> **자료 성격이 글마다 다르다 — 중요하다.**
> `Inside the Magic Pocket`(2016-05, James Cowling)은 **버린 대안을 제대로 적었다** —
> 쿼럼 프로토콜·DHT·Paxos·자체 KV 를 전부 버리고 **샤딩된 MySQL** 을 골랐고, 이유가
> '복잡함은 대개 신뢰성의 반대다'와 '엔지니어 여섯 명도 안 됐다'였다.
> 반면 `Scaling to exabytes`(2016-03, Akhil Gupta)는 **성공만 적고 대가를 안 적는다.**
> → 저장 인프라 기능은 **Cowling 글을 축으로** 삼고 Gupta 글은 일정·숫자로만 쓸 것.

> **작업 메모:** `dropbox.tech` 는 WebFetch 로 잘 읽힌다. ⚠️ **기사 URL 을 추측하지 말 것** —
> `scaling-to-exabytes-and-beyond` 는 404 이고 실제 주소는 `magic-pocket-infrastructure` 다.
> 검색으로 실제 주소를 확인하고 들어갈 것. Broccoli 글 주소는 하이픈이 특이하다
> (`/-broccoli--syncing-faster-by-syncing-less`).

> **비교 재료 셋.** ① **'사고 vs 짓고'** — Dropbox 는 떠났고 나머지 20곳은 남았다.
>   Cloudflare 는 아예 인프라가 제품이라 축이 또 다르다.
> ② **'리팩터링으로는 데이터 모델을 못 바꾼다'** — Nucleus 4년 재작성 / Slack Vitess 3년 /
>   Notion 블록 테이블. **셋 다 '전제가 데이터 모델에 박혔다'는 같은 모양이다.**
> ③ **'일부러 시시한 것을 고른다'** — Magic Pocket 이 Paxos 대신 MySQL / Slack 이
>   NoSQL 대신 MySQL 위의 Vitess. 이유도 같다 — 사내에 이미 있는 운영 지식.

**큐 3/3 — 충분.** 다음 대기는 GitHub → LY(LINE).

### 되풀이되는 설계 축

여러 회사에서 같은 모양이 반복해서 나온 것들. 비교 문서의 씨앗이자, 새 회사를 팔 때
"여기도 같은 문제가 있나"를 먼저 물어볼 목록이다.

- **충돌을 해결하는가, 충돌이 안 생기게 만드는가** — Figma 속성 단위 LWW·분수 인덱싱 /
  Shopify 판매 단위당 1행 / 토스 계좌 락 / Discord 요청 병합 / Stripe 멱등 키.
- **몰리는 것을 한 곳에서 합친다** — Discord 요청 병합·Manifold·길드당 음성 서버 1대.
- **터진 뒤 끊는 대신 들어가기 전에 센다** — Discord Semaphore·침묵 억제.
- **격리의 단위가 곧 전환의 단위** — Shopify pod 이동·리전 페일오버·pod 단위 점진 전환.
- **분포에 맞춘 설계는 분포 밖에서 정확히 실패한다** — Slack 여러 샤드 순회가 보통
  사용자에겐 잘 돌고 수백 워크스페이스에선 무너져 50개로 자른 것 / Discord 대형 길드.
- **미리 한계를 찾아 두고 되돌릴 길을 열어 둔다** — Shopify 스케일 테스트·섀도 모드·
  Verifier·성수기 변경 동결 / 토스 카나리 자동 롤백.
