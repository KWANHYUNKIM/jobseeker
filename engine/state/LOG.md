**가장 좋은 자리는 Lepton 의 안전장치다.** 규칙이 정확도가 아니라 **결정성**이었다 —
'한 번 원래 비트로 돌아온 파일은 앞으로도 항상 돌아온다'. 그 위에 세 겹: 사진 40억 장
사전 검증 · **seccomp 샌드박스**(읽기·쓰기 시스템 호출만) · **저장 전 비트 비교**
(비교 중 원본 메모리는 커널이 읽기 전용으로 잠근다). 대가는 처리 비용 두 배.

같은 파일에 대해 어떤 사용자에겐 이득이고 어떤 사용자에겐 손해**다. 그리고 '평균 30%'가
실제로는 절반 13% · 25%가 40% · 10%가 70% 라는 분포다.

논문 2편 다 confirmed 로 달 수 있었다 — **NSDI'17 Lepton 논문은 드롭박스 자신이 쓴 것**이고
(블로그가 기법을, 논문이 배포·검증을 맡는 흔치 않은 짝), RFC 7932 는 Broccoli 의 바탕이며

## 142 (2026-08-21) — GitHub 코드 검색 · Blackbird

**Dropbox 에서 세운 규칙(한 도메인당 최소 두 글)이 첫 적용에서 값을 했다.**
2023년 아키텍처 글(Timothy Clem)에 **2026년 케이스 폴딩 글**(Alexander Neubeck ·
Greg Orzell)을 겹쳤더니 **3년치 성장이 드러났다** — 저장소 4,500만 → **1억 8천만**,
코드 115TB → **480TB**. 한 글만 읽었으면 2023년 숫자를 현재로 적을 뻔했다.
**교훈: 오래된 글로 기능을 쓸 때는 최신 글로 규모를 갱신할 것.**

결정 8건 · 생각 9개 · 그림 4장 · 논문 2편 · 난제 2건. 검증 경고 0건.

**이 글이 좋은 이유는 버린 대안을 숫자로 계산했다는 것이다.** ripgrep 방식을
**2,048코어 완전 병렬**로 가정해도 질의 하나에 96초 = **0.01 QPS**. 그리고 결론이
'느리다'가 아니라 **'비용 효율적으로 확장할 방법이 없다'** — 성능이 아니라 경제성으로
기각했다. Elasticsearch 는 저장소 800만 색인에 몇 달이 걸렸고, 더 근본적으로는
**텍스트 검색엔진의 기본 동작(어간 추출·불용어 제거)이 코드에서는 전부 방해**다.

**난제 1번이 이번 사이클의 발견 — 최적화가 더 큰 최적화를 막고 있을 때.**
조기 종료는 누가 봐도 옳은 코드인데 **데이터 의존 루프 탈출은 그것만으로 벡터화를 막는다.**
고약한 것은 중간 단계다: **분기만 없애고 break 를 남기면 3.1 → 2.6 GiB/s 로 느려진다** —
옳은 방향으로 한 걸음 갔는데 지표가 나빠지고, 여기서 되돌아가면 영영 못 찾는다.
답은 **'무엇이 느린가'가 아니라 '무엇이 켜지지 않았는가'** — 벡터 명령 개수를 셌다(0 → 41).
**프로파일러는 '하지 못하게 된 일'을 기록하지 않는다.**

난제 2번은 구조에서 나왔다 — **중복 제거와 국소성은 같은 축의 양 끝이다.**
블롭 ID 샤딩이 중복을 없애는(115TB → 고유 28TB) 대신 **모든 질의를 모든 샤드로** 보낸다.
GitHub 은 판 것의 값을 다른 데서 깎았다 — 샤드 하나가 코어 하나로 p99 100ms.

논문 2편은 GitHub 이 **자기 '기하 필터'를 MinHash·HyperLogLog 부류라고 스스로 분류**해서
달 수 있었다. takeaway 를 '정확할 필요가 없는 질문이었다'로 썼다 — 크롤 순서만 정하면
되므로 근사로 충분하다는 것이 이 선택의 핵심이다.
