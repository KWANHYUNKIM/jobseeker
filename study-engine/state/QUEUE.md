# 대기열 — 쓸 낱말

`validate.py --gaps` 의 사다리 3순위가 이 파일의 "대기" 표 **맨 위 한 줄**을 읽는다.
표의 첫 열(낱말)만 기계가 읽는다 — 나머지 열은 사람과 다음 사이클을 위한 근거다.

> ⚠️ 이 문서를 스크립트로 고칠 때 `s.index("## 대기")` 로 자르지 말 것.
> 위 문장에 같은 글자가 있어 인트로 한가운데를 잘라 먹는다. `"\n## 대기"`(줄 시작)로 찾는다.

큐에 올릴 자격은 셋 중 하나다 (PROMPT.md 2⁗단계).
**(a) 수요가 큰데 문서가 없다** / **(b) 이미 쓴 문서가 계속 가리킨다(끊긴 `related`)** /
**(c) 공고·블로그에는 나오는데 어디에도 설명이 없는 말.**

## 대기

| 낱말 | slug | 왜 이 낱말 | 무엇을 읽을 수 있나 |
|---|---|---|---|
| SSE | `sse` | **`grpc` 가 남긴 빈칸이다.** 그 문서가 스트리밍 넷을 다루고 `kafka`·WebSocket·`mqtt` 자리 구분표까지 만들었는데, **브라우저에서 서버→클라이언트 한 방향**이라는 칸이 비어 있다(gRPC-Web 이 못 하는 바로 그 자리). **177건(모집중 52)** 이고 문장이 구체적이다: `SSE 기반 실시간 동기화 구현`(아치서울), `실시간 스트리밍(SSE 또는 WebSocket)을 구현해본 경험`(유메타랩), `WebSocket, Server-Sent Events(SSE) 등을 활용한 데이터 처리`(큐빅), `SSE, RabbitMQ 등을 활용한 실시간 데이터 및 비동기 이벤트 처리`(피트인). 축: ①**롱폴링 → SSE → WebSocket** 의 계단(무엇이 부족해서 다음이 나왔나) ②**그냥 HTTP 라서 얻는 것**(프록시·인증·압축이 그대로 되고 **자동 재접속과 `Last-Event-ID` 로 이어받기**가 규격에 있다) ③**한 방향이라 잃는 것**(클라이언트→서버는 따로) ④**연결 수 한계**와 HTTP/1.1 의 제약 ⑤**LLM 토큰 스트리밍이 왜 대부분 SSE 인가** — 지금 가장 실용적인 각 | **WHATWG HTML 명세의 Server-Sent Events 절**과 **MDN `EventSource`** 가 1차 자료. **URL 은 `WebSearch` 로 확인하고 건다** |
| 무중단 배포 | `zero-downtime-deploy` | **`slo` 가 끝난 다음 줄이다** — 그 문서는 "예산이 남으면 배포한다"까지 갔는데, **그 배포를 어떻게 안전하게 하느냐**는 안 다뤘다. **70건(모집중 26)**: `Docker 기반 Blue/Green 무중단 배포 파이프라인 유지보수`(드랩), `무중단 배포(Blue-Green, Canary 등) 전략 수립 및 릴리스 프로세스 정착`(피에프씨테크놀로지스), `무중단 배포·롤백·백업·장애 복구 체계 운영`(피트인), `무중단 전환·롤링 업데이트 시 데이터 일관성`(크립토랩 — **데이터 쪽 함정을 정확히 짚은 문장**). 축: ①롤링·블루그린·카나리가 **각각 무엇을 사고 무엇을 파는가**(자원 비용 vs 폭발 반경 vs 복잡도) ②**카나리 판정은 지표로 한다** → `slo`·`observability` 와 직결 ③**진짜 어려운 것은 코드가 아니라 스키마다** — expand/contract, 두 버전이 동시에 같은 DB 를 본다(`sharding` 의 backfill·`cdc` 의 스키마 합의와 같은 계열) ④**롤백이 되는가**(마이그레이션은 대개 안 된다) ⑤세션·연결·긴 요청의 배수(drain) | Kubernetes 공식 문서의 **Deployment 롤링 업데이트·`maxSurge`/`maxUnavailable`** 이 확실한 1차 자료. 블루그린·카나리 일반론은 **확인한 범위를 밝힌다.** URL 은 `WebSearch` 로 확인 |
| CQRS · 이벤트 소싱 | `cqrs` | **`cdc` 의 다음 칸이다** — 그 문서가 "읽기용 사본을 만든다"였다면 여기는 **그 분리를 아키텍처로 삼는 것**이다. **29건(모집중 16)** 인데 **실명 기업의 구체적 문장**이 많다: `결제 상태 관리에 Event Sourcing 기술을 도입 및 활용하고 있습니다`(코리아포트원), `CQRS, 이벤트 소싱 등 아키텍처 패턴을 이해하고 실제 시스템에 적용한 경험`(카카오페이증권), `MSA 기반 고가용성 시스템에서 EDA·CQRS·분산 트랜잭션 아키텍처를 방향 설정`(페이타랩), `CQRS(Command Query Responsibility Segregation)를 이해하는 분`(힐링페이퍼). 축: ①**읽기와 쓰기를 다른 모델로 나눈다**는 것뿐(그 이상을 뜻하지 않는다 — 오해가 가장 많은 낱말) ②**이벤트 소싱은 별개다** — 상태 대신 **사건을 저장**한다 ③그래서 **읽기 모델은 항상 늦는다**(최종 일관성 → `slo` 의 신선도) ④**이벤트를 못 고친다**(스키마 진화·업캐스팅 — `grpc` 필드 번호와 같은 계열) ⑤**대부분의 서비스에는 과하다** — 어디까지가 값어치인가 | ⚠️ **1차 자료가 애매한 낱말이다.** 표준도 공식 문서도 없고 블로그·강연이 대부분 — **누가 무엇을 정의했는지 밝히고**, 못 찾으면 "찾지 못했다"고 적는다(`distributed-lock` 의 논쟁 처리와 같게). Microsoft Learn 의 아키텍처 패턴 문서가 후보 |
| DLQ · 재처리 | `dlq` | **이 백과사전이 네 번 멈춘 자리다** — `kafka`·`backpressure`·`circuit-breaker`·`idempotency` 가 전부 "그래서 **실패한 메시지는 어디로 가나**"에서 끝났다((b) 유형). 건수는 **12건(모집중 9)** 으로 적지만 문장이 유난히 구체적이다: `DLQ·백프레셔·서킷브레이커 등 신뢰성 패턴을 상황에 맞게 선택·적용`(사줘 — **셋을 나란히 적었다**), `Retry, DLQ, Backoff 등을 활용해 Queue 처리와 외부 API 연동의 무결성을 보장`(스펙터), `DLQ 설계·재처리 전략 — 예외 필터 DLQ 적재 Slack 알림 재처리`(버블탭 — **운영 절차까지**). 축: ①**독약 메시지**(poison message)가 큐 전체를 멈추는 문제 ②재시도 몇 번 뒤 어디로 보내나 ③**지수 백오프와 지터** ④**DLQ 는 쌓아 두는 곳이 아니다** — 알림·조사·재처리 절차가 없으면 그냥 무덤 ⑤**재처리가 중복을 만든다**(→ `idempotency`) | AWS SQS **dead-letter queue** 문서와 **Kafka(또는 Spring Kafka) 의 재시도·DLT** 문서가 후보. **URL 은 `WebSearch` 로 확인하고 건다** |
