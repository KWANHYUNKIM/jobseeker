# 벽이 되는 것은 크기가 아니라 개수다

> 비교 대상: LY `hdfs-bridge` · Grab `iceberg-lake`·`counter-service` ·
> Discord `voice-sfu` · Notion `logical-shard-reshard`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> 논리를 그대로 두고 물리만 옮기는 이야기는 비교 문서 `두 시스템을 나란히 돌려 옮기기` 에,
> 절충 대신 축을 바꾼 사례는 `양 끝 중 하나를 고르지 않는 법` 에 있다.
> 여기서는 **무엇이 한계를 정하는가**만 본다.

용량 계획은 대개 **얼마나 큰가**로 이야기된다 — 몇 테라바이트, 몇 엑사바이트. 그런데 다섯
사례에서 실제로 먼저 무너진 것은 크기가 아니라 **개수**였다. 그리고 그 개수는 **데이터가 아니라
데이터를 관리하는 쪽**에서 값을 받았다.

## 무엇의 개수가 무엇을 정했는가

| | 세는 대상 | 그것이 정하는 것 | 크기는? |
|---|---|---|---|
| LY `hdfs-bridge` | **파일 개수** | HDFS **네임노드 힙(메모리)** — 파일마다 메타데이터를 들고 있다 | 데이터 양은 한계를 정하지 않는다 |
| Grab `iceberg-lake` | **파일 개수 · 파티션 수** | **S3 API 비용**과 **질의 계획 시간**(HMS 목록 조회가 **O(n)**) | ML 데이터셋은 **평균 1MB 미만**인데 파티션당 **수천 개** |
| Grab `counter-service` | **레코드 개수** | **인덱스 메모리** — 주 인덱스가 **레코드당 64바이트**, RAM 상주 | 데이터는 SSD 에 잘 들어가 있었다 |
| Discord `voice-sfu` | **참가자 수** | **P2P 연결 비용** — *"참가자 수가 늘수록 감당할 수 없이 비싸진다"* | 통화 하나의 데이터는 작다 |
| Notion `logical-shard-reshard` | **논리 샤드 수** | **이사 여부** — 개수를 바꾸면 키가 바뀌고 **데이터가 실제로 이사해야 한다** | — |

**앞의 넷은 개수가 벽으로 다가온 사례이고, 마지막 하나는 개수를 아예 못 바꾸게 고정한 사례다**
(이 분류는 이 사이트의 해석). Notion 은 논리 샤드를 **480개로 두고 바꾸지 않는다** — 개수가
**계약**이 된 셈이다.

## 왜 개수가 먼저 무너지는가

세 사례에서 이유가 같은 모양이다 — **관리하는 쪽이 대상마다 고정된 값을 치른다.**

- **LY** — HDFS 네임노드는 **파일 하나하나의 메타데이터를 메모리에** 들고 있다. 그래서 한계를
  정하는 것이 **데이터의 양이 아니라 파일의 개수**다.
- **Grab `counter-service`** — Aerospike 주 인덱스는 **레코드당 정확히 64바이트**를 RAM 에서 쓴다.
  수십억 레코드면 **데이터가 SSD 에 잘 들어가 있어도 인덱스가 먼저 RAM 을 채운다.**
- **Grab `iceberg-lake`** — S3 는 **요청 단위로** 값을 받고, HMS 의 목록 조회는 **파티션 수에
  선형**이다. 파일이 작을수록 개수가 늘고, 개수가 늘수록 둘 다 나빠진다.

**즉 '작은 파일 문제'는 파일이 작아서 생기는 것이 아니라, 작으면 개수가 늘기 때문에 생긴다**
(이 문장은 이 사이트의 해석).

## 그리고 개수를 늘리는 것은 대개 '좋은 것'이다

이 축이 까다로운 이유가 여기 있다 — 개수를 늘리는 행동이 **다른 목적에서는 옳은 선택**이다.

| 개수를 늘린 것 | 그 자체로는 옳은 이유 |
|---|---|
| **분산 실행**(LY: Spark 출력) | 병렬로 쓰면 빠르다 — 쓰는 쪽마다 파일이 생길 뿐이다 |
| **잘게 나눈 파티션**(Grab) | 필요한 것만 읽으려면 잘게 나눠야 한다 |
| **버킷마다 행**(Grab 카운터) | 시간 창별로 세려면 창마다 자리가 필요하다 |
| **참가자 추가**(Discord) | 통화에 사람이 느는 것은 제품이 잘되는 것이다 |

**빨라지려고 쪼갠 것이 저장 계층의 한계를 당기고, 잘 되려고 늘린 것이 비용을 당긴다**
(이 문단은 이 사이트의 해석).

## 무엇으로 막았는가

| | 대응 | 성격 |
|---|---|---|
| LY | **주기적 병합** — 작은 파일이 지나치게 많은 테이블을 찾아 합치고, Spark 출력은 손으로 관리 | **관리로 눌러 둔다** — 근본 해결이 아니다 |
| Grab `iceberg-lake` | **테이블 형식 자체를 바꾼다**(Iceberg) — 가장 값진 표부터 | **구조를 바꾼다** |
| Grab `counter-service` | **레코드를 줄인다** — 한 카운터의 모든 버킷을 **한 레코드 안의 맵**으로 접는다 | **세는 단위를 바꾼다** |
| Discord | **서버를 가운데 둔다**(SFU) — P2P 를 포기한다 | **위상을 바꾼다** |
| Notion | **개수를 불변으로 고정한다**(논리 샤드 480개) | **애초에 안 늘린다** |

**다섯 중 '더 크게 사서' 해결한 곳이 하나도 없다**(이 문장은 이 사이트의 해석). 메모리를 늘리거나
노드를 붙이는 대신, 넷은 **세는 단위나 구조를 바꿨고** 하나는 **개수 자체를 계약으로 만들었다.**

## 각자가 감수한 것

- **LY** — **끝나지 않는 관리를 감수했다.** 병합은 계속 돌아야 하고, 회사도 이것을 해결이 아니라
  남은 과제로 적었다.
- **Grab `iceberg-lake`** — **이관 비용을 감수했다.** `TIMESTAMP_NTZ`↔`TIMESTAMP_LTZ` 충돌, HMS
  **좀비 락**, **메타데이터 생성 중 저장 계층 비용 급등**까지 겪으며 우선순위를 정해 옮겼다.
- **Grab `counter-service`** — **레코드 단위 TTL 을 잃었다.** 한 레코드에 모든 버킷이 들어 있으니
  **전부 만료되거나 아무것도 만료되지 않아서**, 잘라 내는 일을 직접 하게 됐다.
- **Discord** — **서버를 거치는 비용을 감수했다.** 대신 두 가지를 함께 얻었다 — 참가자끼리
  **IP 가 노출되지 않고**, 문제가 된 사용자의 **오디오 패킷을 서버에서 버릴 수 있다.**
- **Notion** — **논리 샤드를 늘릴 수 없게 됐다.** 대신 물리 배치를 바꿔도 **키가 그대로라 데이터가
  이사하지 않는다.**

## 이 사이트에 아직 없는 것

- **개수를 잘못 세어 용량 계획이 틀어진 사례.** 다섯 다 **원인을 알아낸 뒤에 쓰인 글**이라,
  크기만 보고 계획했다가 개수에서 무너진 과정 자체는 어느 회사도 적지 않는다(**추정**).
- **병합·정리의 비용.** LY 는 주기적 병합으로 눌러 두는데 **그 병합이 얼마나 드는지** 숫자가 없다.
- **개수 상한을 미리 정해 둔 사례가 하나뿐이다.** Notion 의 480개가 유일하고, 나머지 넷은
  **벽에 부딪힌 뒤에** 대응했다.
- **Grab `counter-service`의 맵 항목 수 상한**은 회사가 *"유계"* 라고만 하고 값을 밝히지 않는다 —
  즉 개수를 줄이는 해법에도 **다시 개수 문제가 붙어 있다**(**추정**).

## 읽는 사람에게

이 다섯이 함께 말하는 것은 **"파일을 크게 만들어라"** 가 아니다. 개수를 늘린 행동들은 각각
**그 자리에서 옳은 선택**이었다 — 병렬로 쓰고, 잘게 나누고, 창마다 세고, 사람을 더 부르는 것.

말하는 것은 이쪽이다 — **한계를 정하는 쪽은 데이터가 아니라 그것을 관리하는 쪽이고, 관리하는
쪽은 대개 개수로 값을 받는다.** 네임노드는 파일마다 메모리를, 인덱스는 레코드마다 64바이트를,
S3 는 요청마다 요금을, 메타스토어는 파티션마다 조회 시간을 받는다.

그래서 용량을 볼 때 **"몇 바이트인가" 옆에 "몇 개인가"를 나란히 두는 것**이 이 다섯 사례가
공통으로 가리키는 습관이다(이 문단은 이 사이트의 해석).
