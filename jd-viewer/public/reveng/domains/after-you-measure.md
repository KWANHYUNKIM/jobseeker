# 재 보고 나서 — 숫자가 그대로 답이 된 적이 없다

> 비교 대상: Careem `cost-leaks` · Zerodha `log-storage` · Yelp `partition-access` ·
> Doximity `prod-profiling` · Target `repurchase-timing`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> 재던 자가 틀렸음을 알아채는 이야기는 비교 문서 `잘못된 자를 어떻게 알아채는가` 에,
> 정답이 어디서 오는가는 `무엇을 좋다고 부를 것인가` 에 있다.
> 여기서는 **자는 멀쩡한데 나온 값이 예상과 달랐을 때, 그다음에 무엇을 골랐는가**만 본다.

재 보고 골랐다는 이야기는 대개 **승자**로 전해진다 — 벤치마크를 돌렸더니 이게 이겼다.
그런데 다섯 사례에서 **잰 값이 그대로 답이 된 경우가 하나도 없다.** 이긴 것을 안 고르거나,
낮게 나온 값을 착시로 읽거나, 아예 부정확한 자를 일부러 골랐다.

가장 분명한 증거가 Target 에 있다. 재구매 모델 셋을 **NDCG@10 과 학습 시간으로 나란히 재고
가장 정확한 것을 떨어뜨렸다** — 협업 필터링을 쓰는 SLRC 가 **0.143 / 1300시간**이었는데,
고른 것은 **SLH-BIA 0.131 / 250시간**이다. **정확도 약 9% 를 시간 5배로 사지 않기로 한 것**이다
(이 계산과 표현은 이 사이트의 것).

## 잰 값이 무엇을 뒤집었는가

| | 재기 전의 예상 | 실제로 나온 값 | 그래서 고른 것 |
|---|---|---|---|
| Careem `cost-leaks` (저장) | **지우면 줄어든다** | 지우는 중 지연이 **20ms** — 업무 SLA 는 **1ms**. 원인은 삭제가 아니라 언두 로그 처리(**HLL 58.7억 · 언두 5.7TB**) | **지우지 않고 옮겨 담는다** — DMS Serverless 로 새 인스턴스에. **270TB → 78TB** |
| Careem `cost-leaks` (전송) | **압축하면 CPU 를 더 쓴다** | **Gzip 의 CPU 가 낮게** 나왔다 | 그 값을 **착시로 읽고 버린다** — **프로듀서가 놀고 있어서**. **LZ4** 를 골랐다(저장 88.2% 절감, CPU +8.3%) |
| Zerodha `log-storage` | 로그는 검색해야 하니 색인해야 한다 | 색인 때문에 **저장 요구량이 원본의 **최소 3~4배**로 부푼다**. 컬럼 저장으로 옮기니 **6,500만 행이 22.1GB → 1.13GB** | **색인 대신 압축.** 행당 **340바이트 → 17.38바이트**, 시간당 **$2.67 → $1.14** |
| Yelp `partition-access` | 정확한 접근 기록이 필요하다 | 정확한 쪽(CloudTrail 데이터 이벤트)은 **100만 건당 $1**, 부정확한 쪽(서버 접근 로그)은 **버킷당 $0.25 정액** | **부정확한 쪽을 산다.** **누락되거나 늦게 오거나 중복될 수 있다** — 실제로 **9일 뒤** 도착한 것도 있었다 |
| Doximity `prod-profiling` | 느린 코드가 있을 것이다 | 플레임그래프를 **넓이로 읽으면 손댈 곳이 없었다**. **반복 횟수**로 읽으니 **그 두 단계가 각각 60번 돈다** | 원인은 느린 코드가 아니라 **캐시가 한 층 낮게 걸린 것.** Redis 조회 **4.5만 번 → 1번**, 잡 p95 **214초 → 69초** |
| Target `repurchase-timing` | 가장 정확한 모델을 쓴다 | **SLRC 0.143 / 1300시간** vs **SLH-BIA 0.131 / 250시간** | **정확도가 낮은 쪽.** 회사의 이유는 성능이 아니라 성질이다 — 협업 필터링이 **BIA 성능에 본질적이지 않기 때문** |

## 뒤집힌 방식이 네 갈래다

**① 이긴 것을 안 고른다.** Target 이 여기다. **표에서 1등이 나왔는데도 안 골랐고**, 이유를
성능이 아니라 **성질**로 적었다. 다만 이 선택이 성립하려면 값을 되사야 한다 — 실제로 뒤에서
Spark Scala 데이터 병렬로 **250시간을 **약 3시간** 으로** 줄인다. ⚠️ **줄인 뒤에도 0.131 이
유지되는지는 글에 없다.**

**② 좋게 나온 값을 의심한다.** Careem 의 Gzip 이 그렇다. CPU 가 낮게 나왔는데 그것을 이득으로
읽지 않고 **프로듀서가 놀고 있어서** 라고 짚었다. **지표 하나만 보면 가장 느린 것이 가장
효율적으로 보인다**(이 표현은 이 사이트의 것). 회사는 여기서 멈추지 않고 **프로덕션 토픽에서
다시 쟀고**, 그래서 벤치마크의 **88.2%** 절감이 실제로는 **1KB Avro 에서 약 45%** 라는 것을 알았다.

**③ 정확한 자를 일부러 안 산다.** Yelp 가 유일하게 **정확성을 가격표에 놓고 팔았다.**
**정확성을 샀다가 아니라 팔았다** 는 자리인데, 여기서 이 회사가 한 걸음 더 간다 — **오차의
방향까지 계산했다.** 늦게 온 로그를 무시하기로 하면서 근거로 **며칠 넘게 늦게 오는 것은
0.001% 미만** 을 대고, **놓친 접근은 '안 쓰인다' 쪽으로 기운다**는 것을 알기에 **지우는 결정이
아니라 내리는 결정**에 쓴다. **부정확한 자를 어디에 쓸 수 있는지까지 정한 사례는 여기 하나다**
(이 관찰은 이 사이트의 것).

**④ 재 보니 원인이 딴 데 있었다.** Careem 의 저장과 Doximity 의 프로파일링이 같은 모양이다.
지우는 것이 문제인 줄 알았는데 **지운 것을 치우는 일**이 문제였고, 느린 코드를 찾는 줄 알았는데
**캐시가 걸린 층**이 문제였다. **둘 다 손대려던 곳과 실제로 손댄 곳이 다르다**(이 정리는
이 사이트의 것).

## 재는 행위 자체가 값을 치른다

이 문서에서 가장 덜 이야기되는 자리다. **네 회사가 각각 다른 방식으로 그 값을 냈다.**

| | 재는 데 든 값 |
|---|---|
| Doximity `prod-profiling` | **진단이 상태를 남긴다** — **실제 DB 에 10만 건을 만드는 잡을 프로파일링하는 것은 읽기 전용 작업이 아니다.** 그리고 **프로파일링은 자기 오버헤드를 더하고 타이밍을 바꾼다** 라서 **프로파일과 벤치마크를 따로** 돌린다 |
| Yelp `partition-access` | **재려고 만든 것이 새 비용이 된다** — 접근 로그가 **하루 TiB 단위**로 쌓인다. 그래서 Parquet 으로 다시 담아 **저장 85% · 객체 수 99.99%** 를 줄였다 |
| Careem `cost-leaks` | **프로덕션 데이터를 벤치마크에 쓴다** — 실제 메시지 **20만 건**(약 4.37MB JSON). 그리고 벤치마크로 끝내지 않고 **프로덕션 토픽에서 한 번 더** 잰다 |
| Zerodha `log-storage` | **한 번 버린 것을 다시 잰다** — 2019년 말(0.4)에 버린 Loki 를 **2021년(2.4)에 다시 벤치마크**했다. 또 안 됐지만, **질의 시간이 고통스럽게 느렸고 대부분의 질의가 타임아웃** 이라는 근거가 남았다 |

**Doximity 가 여기서 한 문장을 더 준다** — **프로파일러는 나머지 관측 스택 위가 아니라 옆에
놓인다**, **프로파일러는 쓰기에 너무 만족스러워서 첫 수로 삼고 싶어진다. 그러면 안 된다.**
정밀 도구는 **한 프로세스의 한 순간을 재는** 것이라 **어디를 볼지 모르는 상태에서는 소용이 없다.**

## 버린 대안에 값을 매긴 곳

**셋이 대안을 숫자로 환산해 버렸다.** 이게 이 문서에서 가장 실용적인 부분이다(이 정리는
이 사이트의 것).

- **Careem** — 언두 로그가 자연 감소하기를 기다리는 안을 **시간으로 계산해서** 버렸다:
  **58.7억에서 10만으로 줄이는 데 **약 3.5개월****. **그 숫자가 없었다면 **언젠가는 줄어든다**
  와 **일정에 안 맞는다** 를 비교할 수 없었을 것이다.**
- **Yelp** — **$1 / 100만 건 대 $0.25 정액**. 자릿수가 다르다는 것을 회사가 **자릿수가 다를 수
  있다** 로 적는다.
- **Target** — **1300시간 대 250시간**, 그 값으로 산 것이 **NDCG 0.012**.

**반대로 Zerodha 와 Doximity 는 버린 쪽에 값을 안 매겼다.** Zerodha 는 cLoki 를 버리면서 이유를
넷 들지만 전부 **'우리가 조절할 수 없다'** 쪽이고 가격 비교가 없다. Doximity 는 계측형 프로파일러를
안 쓰는 이유를 성질로만 적는다. **값을 매길 수 있는 대안과 없는 대안이 갈린다**(이 구분은
이 사이트의 것).

## 이 사이트에 아직 없는 것

- **잘못 고른 사례가 없다.** 다섯 다 재 보고 고른 것이 맞았다는 서술로 끝난다. **재 보고
  골랐는데 틀렸다는 글을 아직 못 찾았다** — 회사가 자기 블로그에 쓰는 글이라 당연할 수도
  있다(**추정**).
- **다시 재 본 이야기가 거의 없다.** Zerodha 만 2년 뒤 Loki 를 다시 쟀다. 나머지 넷은
  **고른 뒤에 그 선택을 재검토했다는 기록이 없다** — Careem 의 LZ4 도, Target 의 SLH-BIA 도
  지금 잘 돌고 있다는 데까지다.
- **재는 비용을 절감과 나란히 적은 곳이 없다.** Yelp 의 접근 로그가 하루 TiB 씩 쌓이는데
  **그 비용이 33% 절감 안에 들어 있는지 밖에 있는지 알 수 없다.**
- **표에서 진 쪽의 이야기가 없다.** Gzip 이 왜 그렇게 느린지, SLRC 가 왜 1300시간이 드는지는
  그쪽 설계에 이유가 있을 텐데 **이 사이트는 고른 쪽만 읽었다.**
