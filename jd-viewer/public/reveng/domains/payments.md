# 결제 — 되돌릴 수 없는 일을 다루는 네 가지 방식

> 비교 대상: 토스 `payment-approval` · Stripe `idempotent-payments`·`api-surface` ·
> Shopify `checkout-reservations` · 네이버 `fast-settlement`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.

결제는 되돌리기 어렵다. 그래서 이 도메인의 설계는 대부분 **"잘못됐을 때 어떻게 하나"**에 대한 답이고,
네 회사가 그 답을 서로 다른 곳에 놓았다.

그리고 Shopify 를 넣으면 질문이 하나 더 생긴다 — **잘못되기 전에 무엇을 붙잡아 두는가.**

먼저 눈에 띄는 건 **셋이 같은 장치를 쓴다**는 것이다. 토스·Stripe·Shopify 모두 멱등 키로
중복 요청을 막는다. 그런데 **그 계약을 어디까지 문서로 밝히는지가 세 단계로 갈린다.**

## 같은 장치, 어디까지 밝히는가

| | 토스 `payment-approval` | Stripe `idempotent-payments` | Shopify |
|---|---|---|---|
| 멱등 키를 쓰는 곳 | **취소 요청** — 두 번 환불되는 것을 막는다 | **모든 POST** — GET·DELETE 는 정의상 멱등이라 보내지 말라고 명시 | **부작용이 있는 작업** — 카드 결제 · 구독 청구 시도 · 매출 확정 |
| 키를 만드는 주체 | 가맹점 | 클라이언트(V4 UUID 권장, 최대 255자) | 클라이언트(UUID 권장), 인자 `idempotencyKey` 또는 `@idempotent(key:)` 디렉티브 |
| 보관 기간 | **15일** | **최소 24시간** 뒤 제거될 수 있음 | **문서에 없다** |
| 재생하면 무엇이 오나 | 첫 결과 | 첫 요청의 **상태 코드와 본문** — 성공·실패 무관, **500 오류까지 그대로** | **문서에 없다** — "반복 요청은 몇 번을 재시도해도 한 번만 실행된다"까지 |
| 특이 사항 | — | — | **벌크 뮤테이션은 행 단위로** 멱등성이 적용된다 |

**계약을 얼마나 촘촘히 적어 두는지가 회사마다 다르다**(이 문장은 이 사이트의 해석). Stripe 는
재시도했을 때 무엇이 오는지까지 약속해서 클라이언트가 그 위에서 로직을 짤 수 있게 하고,
Shopify 는 '한 번만 실행된다'는 결과만 약속한다. **약속하지 않은 것은 바뀔 수 있다**는 뜻이기도
하다(이 역시 추정).

그리고 Shopify 쪽에는 키 자체에 대한 재미있는 사실이 하나 더 있다. **UUIDv4 에서 ULID 로
바꾸자 한 고처리량 시스템에서 INSERT 시간이 50% 줄었다** — 멱등 키는 계약이면서 동시에
데이터베이스에 계속 쌓이는 행이기도 하다(뒷문장은 이 사이트의 해석).

## 실패를 상태로 남기는가, 되돌리는가

두 번째 축이 이 비교에서 가장 선명하다. **같은 사건을 두 회사가 정반대로 모델링한다.**

**토스는 실패의 종류를 상태로 남긴다.**
- `ABORTED` — 승인을 **시도했으나 실패**한 것
- `EXPIRED` — 인증까지 끝났는데 **30분 안에 시도조차 못 한** 것

둘은 다른 사건이므로 다른 상태다. 회사가 밝힌 이유는 **"왜 이 주문에 돈이 안 들어왔는가"를
나중에 되짚기 위해서**다. 대가는 가맹점이 다뤄야 할 분기가 늘어난다는 것.

**Stripe 는 실패를 상태로 남기지 않는다.**
결제 시도가 실패하면(카드 거절 등) PaymentIntent 의 상태가 **`requires_payment_method` 로
되돌아간다.** 손님이 다른 카드를 내는 현실이 그대로 모델에 담겨 있다. 대가는 **상태가 앞뒤로
오가서 현재 상태만 봐서는 몇 번 실패했는지 알 수 없다**는 것이고, 실제로 confirm 을 너무 여러 번
하면 자동으로 `canceled` 가 되기도 한다.

| | 토스 | Stripe |
|---|---|---|
| 실패 후 상태 | `ABORTED`(시도했으나 실패) / `EXPIRED`(시도 못 함) | `requires_payment_method` — 처음으로 되돌아감 |
| 실패의 종류 구분 | **상태로 구분한다** | 상태로는 구분하지 않는다 |
| 재시도의 단위 | 새 결제 세션(추정) | **같은 PaymentIntent** |
| 알기 쉬운 것 | 무엇이 왜 실패했는가 | 지금 무엇이 필요한가 |
| 알기 어려운 것 | 시도가 몇 번 이어졌는가(추정) | **몇 번 실패했는가** |

**한쪽은 과거를 남기고 다른 쪽은 현재를 가리킨다**(이 대비는 이 사이트의 해석).

## 되돌릴 수 없는 일 앞에서 무엇을 미리 붙잡는가

Shopify 만 다른 자리에 서 있다. 이 회사에서 결제는 **혼자 일어나는 사건이 아니다** — 결제가
성공하는 순간 **물건 하나가 세상에서 줄어야** 한다. 그래서 문제가 '결제를 어떻게 되돌리나'
앞으로 옮겨간다.

> 한쪽으로 틀리면 **두 구매자가 같은 마지막 하나를 산다** — 상인이 주문을 취소하고 사과 메일을
> 보내고 지원 비용을 문다.

그래서 결제가 진행되는 동안 그 물건을 **붙잡아 둔다**(예약). 결제가 성공하면 **청구**로
원장에서 영구히 뺀다. 여기서 나온 결정들이 이 문서의 다른 세 회사와 성격이 다르다.

| | Shopify `checkout-reservations` |
|---|---|
| 무엇을 붙잡나 | **판매 가능한 단위마다 한 행** — 재고 10개면 10행. `SKIP LOCKED` 로 잠기지 않은 행을 집는다 |
| 왜 행으로 나눴나 | 수량 컬럼 하나면 동시 요청이 **모두 같은 행에 줄을 선다**(뒷부분은 이 사이트의 해석) |
| 폭발을 막는 법 | 아이템/로케이션당 **가용 행 1,000개 상한** + 소진 시 인라인 보충(락으로 한 트랜잭션만) |
| 정확성 기준 | **재고가 있는 구매자에게 품절이라고 말하지 않는다** |
| 이전에 무엇이 문제였나 | 예약은 Redis · 원장은 MySQL 이라 청구가 **원자적으로 묶을 수 없는 두 트랜잭션** → 오버셀 · 언더셀 · 예약 유실 |

**세 회사는 되돌리는 방법을 설계하고, Shopify 는 되돌릴 일이 생기지 않도록 미리 붙잡는다**
(이 대비는 이 사이트의 해석). 그리고 그 이유가 서 있는 자리에서 나온다 — 실패의 비용을 무는
쪽이 우리가 아니라 **상인**이기 때문이다.

## 가맹점 코드를 깨지 않으면서 API 를 바꾸기

세 번째 축. 두 회사가 같은 제약 — **이미 연동한 가맹점은 자기 코드를 고치지 않아야 한다** — 아래에서
정반대 방향으로 갔다.

**토스는 어댑터를 둔다.** 10년 된 결제창을 다시 쓰면서 가맹점이 보내는 수백 개의 평평한
파라미터를 **Converter** 가 흡수해 도메인 객체로 바꾼다. 그래서 비즈니스 로직은 '어느 시대의
파라미터로 들어왔는지'를 몰라도 된다. 그리고 버전을 경로 최상단에 두고 **각 버전을 완전히
독립된 API 로** 관리한다.

**Stripe 는 생성기를 둔다.** OpenAPI 를 단일 정규 형식으로 삼아 v1 Ruby DSL 과 v2 Protocol
Buffer DSL 양쪽에서 생성하고, 그 하나의 스펙에서 API Reference·코드 스니펫·**7개 언어 SDK**·CLI
까지 자동으로 흘려보낸다. 머지 전에 자동 테스트가 역호환성을 검사한다.

| | 토스 | Stripe |
|---|---|---|
| 방식 | **어댑터** — 옛 입력을 흡수 | **생성 파이프라인** — 하나의 스펙에서 만들어 뿌림 |
| 버전 관리 | 경로 최상단에 버전, 버전별 완전 독립 | 릴리스마다 OpenAPI 스냅샷을 정식 설명으로 저장 |
| 유지 비용 | **버전 수만큼 선형으로 증가** | 파이프라인 하나에 집중 |
| 감수한 것 | **오래된 버전이 언제 죽는지 아무도 모르게 된다** | **v1 의 과거 버전은 설명을 다시 만들 수 없다** |
| 하류에 닿는 범위 | API 응답 | API + 문서 + 스니펫 + SDK + CLI |

**두 방식 모두 과거를 완전히 놓지는 못한다**(추정). 토스는 옛 버전이 영원히 살아남고, Stripe 는
옛 버전이 되살아나지 못한다 — 방향만 반대다. 이 축을 더 넓게 본 것은 비교 문서
`옛 약속을 어떻게 지키는가` 에 있다.

## 틀렸다는 걸 나중에 어떻게 아는가

멱등 키도 상태 모델도 **그 순간**을 다루는 장치다. 그런데 시간이 지난 뒤 우리 장부와 상대의
장부가 어긋나 있으면 그건 다른 문제다.

이 질문에 답한 것은 Shopify 다 — **금융 파트너와 상시 대조(reconciliation)** 해서 개별 청구와
환불, 그리고 잔액 총계가 맞는지 확인하고, **불일치를 데이터베이스에 기록한 뒤 가능하면
자동으로 교정**한다. 회사는 이렇게 해야 불일치가 **구조적인 문제로 자라지 않는다**고 밝힌다.

같이 나온 관행 두 가지도 이 도메인을 읽는 데 쓸모가 있다.
- **타임아웃을 낮춘다** — 오픈 1초, 읽기/쓰기 5초가 출발점. Ruby `Net::HTTP` 의 기본 60초는
  사용자 앞에 있는 요청에는 너무 길다.
- **용량은 70~80%에서 이미 큐가 자란다** — 리틀의 법칙(용량 = 처리량 × 지연)으로 따지면
  완전 포화는 안전하게 도달할 수 없는 지점이다.

## 네이버는 다른 질문에 서 있다

네 회사 중 네이버만 질문 자체가 다르다. 거래가 자기 안에서 일어나니 '어떻게 승인할까'는 문제가
아니고, 대신 **'언제 판매자에게 돈을 줄까'**가 1급 질문이 된다.

판매자가 대금을 8일 기다리는 동안 그 돈은 대출 이자가 된다. 그래서 배송 시작 다음날부터
**약 3일 만에 100%** 를 준다. 그 5일치 위험을 담보 대신 FDS 로 관리하고, 월 20건·반품률 20%
미만이라는 낮은 문턱을 유지한다 — **문턱이 낮다는 사실 자체가 탐지 성능에 대한 베팅이다.**

그리고 이 기능은 **무료다.** 선정산은 원래 수수료를 받는 금융 상품인데 받지 않는다.

**서 있는 자리가 질문을 정한다.** 토스는 가맹점과 카드사 사이에 있어 '어떻게 승인하고 어떻게
되돌릴까'를 묻고, Stripe 는 개발자와 결제망 사이에 있어 '다시 시도해도 되는가'를 계약으로
만들고, Shopify 는 상인의 가게 안에 있어 **'결제가 끝나기 전에 물건을 붙잡아 둘 수 있는가'**를
묻고, 네이버는 자기 커머스 안에 있어 '언제 줄까'를 묻는다.

## 무료로 준다는 것의 의미 (추정)

빠른정산이 그 자체로 수익이 없다는 사실은 이 비교에서 여전히 가장 흥미로운 지점이다. 위험은
지고 대가는 안 받는데, 그러면 어디서 걷는가 — **커머스에 남는 판매자**에서 걷는다.

같은 구조가 다른 회사에도 있다. 카카오톡은 메시지 전달로 돈을 벌지 않고 그 대화가 열리는
지면에서 벌고, 당근은 개인 간 거래에서 수수료를 받지 않고 그 트래픽 위의 광고에서 번다.
이런 **'수익을 옆 도메인에서 걷는' 구조는 기능 하나만 봐서는 보이지 않는다.** 도메인 지도를
그려야 드러난다 — 이 사이트가 회사마다 `domain_map` 을 요구하는 이유다.
(구조 자체는 각 회사가 밝힌 사실이지만, 셋을 같은 종류로 묶는 것은 이 문서의 해석이다.)

## 이 사이트에 아직 없는 것

- 토스: 웹훅 재전송의 간격과 최대 횟수, 그리고 **멱등 키 15일의 근거**
- Stripe: 멱등 저장소를 어떻게 구현했는지(문서는 계약만 밝힌다), 오래된 API 버전의 지원 기간,
  **키 24시간의 근거**
- Shopify: **멱등 키의 보관 기간과 재생 시 응답**(문서에 아예 없다), 그리고 **결제 승인 자체의
  상태 모델** — 이 사이트가 읽은 것은 재고 예약과 회복탄력성 관행까지다
- 네이버: 빠른정산의 실제 손실률과 회수율

**네 회사 모두 '그 설계의 진짜 비용에 해당하는 숫자'를 공개하지 않는다.** 결제 도메인을 읽을
때는 이 종류의 숫자를 먼저 찾아보고, 없다는 사실 자체를 기록해 두는 편이 낫다.

## 읽는 사람에게

결제 시스템을 볼 때 '어떻게 돈을 받는가'를 먼저 보게 되는데, 네 회사가 실제로 공들인 곳은
전부 그 반대편이었다 — **취소·환불(토스), 재시도(Stripe), 결제 전에 물건 붙잡기(Shopify),
선지급의 위험(네이버).**

그리고 실패를 다루는 방식에서 성격이 갈린다. **과거를 상태로 남길 것인가, 현재를 가리킬
것인가, 아니면 애초에 되돌릴 일이 생기지 않게 미리 붙잡을 것인가.** 어느 쪽도 틀리지 않았지만,
하나를 고르면 다른 쪽 질문에는 답하기 어려워진다.
