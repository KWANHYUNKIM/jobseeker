# 문지기를 무엇으로 세우는가 — 기계가 만든 것을 무엇이 통과시키는가

> 비교 대상: Wix `compile-then-publish`·AirBot · Meituan `align-people-then-machines`·
> `run-it-to-verify`·`binarize-the-rubric` · monday.com `agent-with-guardrails` ·
> Cybozu(반대 방향, 회사 `open_questions`)
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> **자동이 낸 것을 무엇으로 믿는가**는 비교 문서 `기계가 그렇다는데` 에,
> **기계가 아예 판정할 수 없는 것**은 `기계가 판정할 수 없는 것을 어디에 두는가` 에,
> **무엇을 좋다고 부를지**는 `무엇을 좋다고 부를 것인가` 에 있다.
> 여기서는 **문 하나를 실제로 세운 회사들이 그 문을 무엇으로 만들었고, 그 문이 무엇을
> 못 잡는가**만 본다.

에이전트에게 일을 맡긴 이야기는 대개 **무엇을 시켰는가**로 전해진다. 그런데 일곱 사례에서
설계를 실제로 가른 것은 시킨 일이 아니라 **그 결과를 들여보낼지 정하는 자리**였다.
**여섯 회사가 전부 모델을 더 좋게 만드는 대신 문을 하나 세웠고, 그 문의 재료가 다 다르다.**

가장 분명한 자리가 Wix 다. 코드 샘플 **2,000개**를 AI 로 고치면서 *"We couldn't publish
bad code in the reference"* 라고 적고, Velo API 의 타입 정의를 받아 **실제로 컴파일해 통과한
것만** 내보냈다. **모델을 믿을 수 있는지 묻는 대신 결과를 기계로 확인할 수 있는 형태로 만든
것이다**(이 표현은 이 사이트의 것).

## 문을 무엇으로 만들었는가

| | 문지기 | 통과 조건 | 왜 그것이었나 |
|---|---|---|---|
| Wix `compile-then-publish` | **컴파일러** | 타입 정의를 받아 컴파일이 되는가 | *"We couldn't publish bad code in the reference"* |
| Wix AirBot | **타입 정의(Pydantic)** | 자유 텍스트가 아니라 엄격한 타입 JSON 인가 | *"LLMs are inherently non-deterministic, but SRE automation demands reliability"* |
| Meituan `align-people-then-machines` | **AI 감사(Pre-PR)** | AI 가 찾을 수 있는 문제를 다 고쳤는가 | 리뷰가 병목이 되어 AI 로 번 속도가 리뷰 큐에서 다 먹혔다 |
| Meituan `run-it-to-verify` | **샌드박스 실행** | 검증 코드가 실제로 돌아 성공하는가 | 보상 모델은 *"只能判断…在文本层面是否合理，无法验证其在物理层面能否执行"* |
| Meituan `binarize-the-rubric` | **일치율 문턱** | 사람끼리·사람과 기계 일치율이 **85~90%** 를 넘는가 | 넘기기 전에는 기계에게 채점을 맡기지 않는다 |
| monday.com `agent-with-guardrails` | **린터** | AI 가 단 Human Todo 가 남아 있지 않은가 | *"alert the linter to block the PR from merging"* |

**⭐ 여섯이 공통으로 한 일이 하나 있다** — **모델의 정확도를 올리는 대신 모델 바깥에 통과
조건을 만들었다**(이 정리는 이 사이트의 것). Wix 는 *"AI-generated code tends to
over-engineer"* 를 인정하면서도 모델을 손대지 않고 컴파일러를 세웠고, Meituan 은 *"信息质量
比信息量更重要"* 같은 결론을 내면서도 문을 앞으로 옮겼다.

## 그 문이 못 잡는 것 — 대가가 한 방향으로 모인다

**이게 일곱을 관통하는 것이다**(이 정리는 이 사이트의 것). **검사할 수 있는 것만 검사된다.**

| | 문이 확인하는 범위 | 그냥 지나는 것 |
|---|---|---|
| Wix 컴파일러 | *"valid JavaScript and used the Velo APIs correctly"* | **컴파일되지만 예제로서 뜻이 틀린 코드** |
| Wix 타입 강제 | 출력의 **모양** | 모양은 맞는데 내용이 틀린 판단 |
| Meituan AI 감사 | AI 가 볼 수 있는 규범·버그·예외·일관성·확장성·성능 | **AI 가 못 보는 결함** — 그 범위가 어디까지인지 자체가 흐릿하다 |
| Meituan 샌드박스 | 실행되는가 | **코드로 검증할 수 없는 과제는 애초에 만들어지지 않는다** |
| Meituan 이진화 | 예·아니오로 쪼개진 지표 | **이진화가 안 되는 지표** |
| monday.com 린터 | AI 가 스스로 단 Human Todo | **AI 가 '판단이 필요하다' 고 안 본 것** |

**그리고 그 몫이 얼마인지를 적은 회사가 하나도 없다.** Meituan 은 **모름** 비율을 루브릭
품질의 신호로 쓴다고만 하고 그 값을 안 적고, 나머지 다섯은 못 잡는 몫을 아예 세지 않는다.

## 문지기의 성질이 갈린다 — 못 잡는 범위가 분명한가

**여기서 두 갈래가 생긴다**(이 구분은 이 사이트의 것).

**① 못 잡는 범위가 분명한 문지기.** 컴파일러와 타입 정의와 린터가 여기다. 컴파일러가
통과시키는 것이 무엇인지는 **정의로 알 수 있다** — Wix 도 그것을 *"valid JavaScript and used
the Velo APIs correctly"* 까지라고 적는다. 무엇을 못 보는지 알기 때문에 **그 밖은 사람이 본다**
는 설계가 성립한다.

**② 무엇을 못 보는지가 흐릿한 문지기.** Meituan 의 Pre-PR AI 감사가 여기다. **AI 가 규범·
버그·예외·일관성·확장성·성능을 짚는데, 그 각각을 어디까지 보는지는 아무도 모른다.** 회사도
**통합 테스트나 점진 배포 이야기를 적지 않는다**(이 지적은 이 사이트의 것).

**그 흐릿함을 회사가 다른 방식으로 메운다** — **상급 모델이 하급 모델의 출력을 심사하고,
서로 다른 회사의 모델을 교차**시켜 능력이 서로를 메우게 한다. **문지기가 못 보는 것을 다른
문지기로 덮는 셈이다**(이 표현은 이 사이트의 것). ⚠️ **대신 전체가 특정 모델의 가용성에
묶이는데 대체 전략은 적지 않는다.**

## 문을 어디에 둘 것인가 — 두 곳이 앞으로 옮겼다

**Meituan 의 AI 감사는 실패에서 나왔다.** 처음에는 시험 항목을 AI 가 전부 생성하게 했는데
*"AI 缺乏全局业务认知…同时发散出大量无价值的边缘用例，反而增加 Review 负担"*(전체 업무 인식이
없고 값없는 변두리 케이스를 뿜어 **되레 리뷰 부담을 늘린다**)였다. **실패의 이유가 '틀렸다' 가
아니라 '일이 늘었다' 다**(이 정리는 이 사이트의 것).

그다음 리뷰 자체가 병목이 됐다 — **AI 로 번 속도가 리뷰 큐에서 다 먹혔다.** 그래서
*"提交代码前，要求 RD 必须先用 AI 审查代码进行多轮自查"*(제출 전에 개발자가 AI 로 여러 차례 자체 점검해야 한다)로 바꾸고 **사람 리뷰어는
업무 로직만** 보게 했다. **만들어 내는 쪽을 줄이는 대신 들어오기 전에 걸러내는 자리를 만든
것이다.**

**monday.com 도 같은 방향으로 옮겼는데 출발이 반대다.** 사람이 앞단에서 무겁게 검토하는 방식이
*"became bottleneck, not safety mechanism"* 이었고, **앞에서 다 보는 대신 뒤에서 둘이 보는
쪽**으로 갔다. **그리고 그 장치는 사고 뒤에 늘었다** — 셀렉터 이관이 **테스트를 통과했는데
메모이제이션에 숨은 부작용**이 있었고, 그 뒤 **22포인트 AI 리뷰 검증과 비교 테스트와 동결 시
병합 차단**이 붙었다.

## 문지기가 실제로 잡은 것

**Wix 의 결과가 이 문서에서 가장 뜻밖이다.** 컴파일러를 세워 놓고 보니
*"we never saw a single example of the LLM failing to convert the code properly"* 였다.
**잡힌 것은 전부 주변의 문제였다** — **토큰 한도에 걸린 잘림**과 **타입 정의가 API 와 어긋난
몇 건**. 사람은 오류 목록만 봤고 **작성자 6명이 한나절**이면 끝났다.

**⚠️ 다만 이것을 "모델이 정확했다" 로 읽으면 안 된다**(이 지적은 이 사이트의 것) —
**컴파일이 잡을 수 있는 범위 안에서만 확인된 것**이다.

**반대쪽 끝에 Wix AirBot 이 있다.** 타입을 강제하고 최소 권한을 걸었는데도 **완전 자동화율이
15%** 다 — **PR 후보 180개 중 28개만 직접 병합됐고 나머지 85%는 사람 손을 거친다.**
**문을 세운다고 사람이 사라지지는 않는다**(이 정리는 이 사이트의 것).

## 반대 방향 — 너무 많이 잡는 문지기

**Cybozu 가 이 문서에서 유일하게 반대편에 있다.** 다른 여섯은 문지기가 **못 잡는 것**이
문제인데, 여기서는 **너무 많이 잡는 것**이 문제다. 모듈 단위 취약점 스캐너가 오탐을 쏟아 내자
**심볼 단위 도달성 분석**을 붙여 실제로 닿는 것만 남긴다.

**그런데 그 문지기도 같은 자리에서 무너진다** — 바이너리에서 **심볼 정보를 지우면**
(`-ldflags '-s -w'`) 그 모듈의 **모든 취약점에 영향받는 것으로 판정된다.** 그리고 지금은
*"人が介入してバイナリを取り出し"*(사람이 개입해 바이너리를 꺼내야) 한다.
**판정의 재료가 없어지면 문지기는 가장 안전한 쪽으로 기운다**(이 해석은 이 사이트의 것).

## 사람은 어디에 남는가

**여섯 다 사람을 없애지 않았고, 남긴 자리가 갈린다.**

| | 사람이 하는 일 | 얼마나 |
|---|---|---|
| Wix `compile-then-publish` | **검증 오류만** 본다. 변환 탓인지 아닌지를 가른다 | 작성자 **6명이 한나절** |
| Meituan AI 감사 | **업무 로직만** 본다. 나머지는 앞에서 걸러졌다 | 적히지 않음 |
| Meituan 이진화 | **기준을 만든다.** 규모는 기계가 맡는다 | *"人工更应该做高价值标准设计和 Rubric 对齐"*(사람은 값이 큰 기준 설계와 루브릭 정렬을 해야 한다) |
| monday.com | **최소 두 명**이 PR 을 본다. Slack 공지와 보드 갱신도 사람이 | 만든 팀 엔지니어 **7명** |
| Wix AirBot | **PR 의 85%** 를 손본다 | 그래도 월 **675 엔지니어 시간** 절감 |

**⭐ 공통점이 하나 있다** — **자동화가 사람을 없앤 것이 아니라 사람이 볼 것을 목록으로
줄였다**(이 정리는 이 사이트의 것). Wix 는 2,000개가 아니라 오류만, Meituan 은 전체가 아니라
업무 로직만, monday.com 은 앞단 전체가 아니라 뒤의 PR 만 본다.

## 이 사이트에 아직 없는 것

- **문이 못 잡은 것이 실제로 사고가 된 기록이 하나뿐이다.** monday.com 의 셀렉터 이관이
  **테스트를 통과했는데 메모이제이션에 숨은 부작용**이 있었던 건뿐이고, 나머지 다섯은
  **문을 세운 뒤 무엇이 새어 나갔는지를 적지 않는다.** 회사가 자기 블로그에 쓰는 글이라
  당연할 수도 있다(**추정**).
- **못 잡는 몫을 센 곳이 없다.** 컴파일되지만 뜻이 틀린 코드가 몇 %인지, 이진화가 안 되는
  지표가 얼마인지, AI 감사가 놓친 결함이 몇 건인지 **어느 글에도 없다.** 유일하게 가까운 것이
  Meituan 의 **모름** 비율인데 **그 값도 안 적혀 있다.**
- **문지기 자체의 정확도가 없다.** Meituan 은 일치율 문턱을 **85~90%** 로 정하고 **Beam 이
  62%에서 92%로** 올랐다고 적지만, **그 문턱을 넘긴 뒤 기계 채점이 실제로 얼마나 맞았는지**는
  나오지 않는다.
- **문을 여는 비용이 없다.** Wix 는 컴파일을 몇 번 돌렸는지, Meituan 은 AI 감사에 토큰이
  얼마나 드는지, 샌드박스 10만 개를 돌리는 값이 얼마인지 **어느 쪽도 적지 않는다.**
- **문이 틀렸을 때 되돌린 기록이 없다.** monday.com 은 사고 뒤에 검증을 늘렸지만
  **그 검증이 다시 틀린 적이 있는지**는 없고, **문을 완화한 사례는 어디에도 없다.**
