# 양 끝 중 하나를 고르지 않는 법

> 비교 대상: LY `kafka-e2ee` · GitHub `actions-runners` · Dropbox `magic-pocket` ·
> Spotify `rap` · Canva `session-revocations`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> 연속적인 것을 몇 칸으로 자를지의 이야기는 비교 문서 `몇 칸으로 자를 것인가` 에,
> 무엇을 미리 놓아둘지는 `어디에 무엇을 미리 놓아두는가` 에 있다.
> 여기서는 **절충점을 찾는 대신 절충이 걸려 있던 축 자체를 바꾼 사례**만 본다.

설계 이야기의 절반은 손잡이 하나를 어디쯤 둘 것인가로 끝난다 — 조금 더 안전하게, 조금 더 빠르게,
조금 더 싸게. 그런데 다섯 사례에서는 그 손잡이를 돌리지 않았다. **손잡이가 걸려 있던 축을 바꿨다.**

## 무엇과 무엇 사이에 갇혀 있었나

| | 한쪽 끝 | 다른 쪽 끝 | 갇힌 이유 |
|---|---|---|---|
| LY `kafka-e2ee` | 소비자마다 키를 따로 → **격리** | 키 하나를 공유 → **메시지 크기 고정** | 헤더 메타데이터가 소비자 수에 비례해 쌓인다 |
| GitHub `actions-runners` | 환경을 매번 버린다 → **격리** | 환경을 재사용한다 → **속도** | 앞 잡의 찌꺼기가 남으면 결과를 믿을 수 없다 |
| Dropbox `magic-pocket` | SSD 쓰기 캐시를 둔다 → **지연** | 캐시를 뗀다 → **단순함** | 캐시가 빠른 만큼 부품과 고장이 늘어난다 |
| Spotify `rap` | 질의 엔진을 쓴다 → **표현력** | 사본을 따로 만든다 → **속도** | 분산 SQL 엔진은 한 행에도 스케줄링에 초 단위를 쓴다 |
| Canva `session-revocations` | 매번 DB 에 묻는다 → **즉시성** | 쿠키를 믿는다 → **속도** | 믿으면 취소를 전할 길이 없다 |

**다섯 다 '적당한 지점'이 존재하지 않는 종류의 갈등이다**(이 문장은 이 사이트의 해석).
소비자마다 키를 절반만 줄 수는 없고, 환경을 절반만 버릴 수도 없다.

## 축을 어디로 옮겼는가

| | 옮긴 축 | 구체적으로 |
|---|---|---|
| LY | **공간 → 시간** | 공유 KEK 을 쓰되 **주기적으로 회전**한다. 회전 기간에는 활성 키 전부로 DEK 를 감싸 옛 소비자와 새 소비자가 같은 메시지를 함께 읽는다 |
| GitHub | **잡 → 이미지** | 캐시를 잡 안이 아니라 **VM 이미지에** 넣고, 낡지 않게 **하루에 여러 번 이미지를 다시 만든다** |
| Dropbox | **성능 → 운영** | SSD 쓰기 캐시를 **뗀다.** 잃은 것은 지연, 얻은 것은 **월 8~10건의 SSD 고장과 단일 장애점이 사라진 것** |
| Spotify | **빠르게 → 몇 번** | 질의 엔진을 개선하는 대신 **거치지 않는다.** 목표가 '읽기를 빠르게'가 아니라 **'읽기 횟수를 1 또는 0으로'** 가 된다 |
| Canva | **파드 수 → 트래픽** | 폐기 목록을 DB 가 아니라 **S3 에서** 받는다. 부하가 **파드 수·시간 창**이 아니라 **쓰기 처리량·트래픽**에 비례하게 된다 |

**세 사례는 '무엇에 비례하는가'를 바꿨고, 두 사례는 '무엇을 재는가'를 바꿨다**(이 분류는 이
사이트의 해석). Canva 는 부하가 비례하는 대상을 바꿨고, Spotify 는 최적화의 단위를 시간에서
횟수로 바꿨고, GitHub 은 준비 시간이 드는 자리를 잡에서 이미지 빌드로 옮겼다.

## 숫자로 본 결과

| | 얻은 것 | 잃은 것 |
|---|---|---|
| LY | 소비자가 몇이든 **헤더 메타데이터 한 항목**. CPU 증가 **1% 미만**, 2주 롤아웃 중 사고 **0건** | **키가 새면 과거와 미래가 함께 열린다**(회사가 직접 인정). 회전 기간에는 헤더가 활성 키 수만큼 커진다(**추정**) |
| GitHub | 워크플로 **약 50분 → 12분** | **이미지 파이프라인이 상시로 돌아야 한다** — 비용이 사라진 게 아니라 옮겨 갔다(**해석**) |
| Dropbox | 쓰기 처리량 **15~20%** 상승, **월 8~10건 SSD 고장**과 단일 장애점 제거 | **p95 디스크 쓰기 지연 10~15% 악화**(전체 쓰기 지연의 2%). 인메모리 읽기 캐시도 함께 없애 **읽기 지연도 나빠졌다** |
| Spotify | 단건 질의를 **수 KB 범위 읽기 하나**로, 때로는 **읽기 0회**로 | 조회에 맞춰 레이아웃을 바꿀 때마다 **배치 분석이 깎인다** — co-grouping 은 컬럼 프루닝을, 인터리빙은 단일 컬럼 스캔 I/O 를 |
| Canva | 읽기 복제본 **여럿 → 2개**(이중화용). 쓰기 **초당 2,000건 이상** | 폐기가 **즉시 반영되지 않는다** — 30분 청크 창 안에서. 한 청크는 **한 번에 한 워커만** 갱신 |

**얻은 것과 잃은 것이 서로 다른 단위다.** LY 는 크기를 얻고 **위험**을 내줬고, Dropbox 는 처리량과
운영 단순함을 얻고 **지연**을 내줬다. 축을 바꾼다는 것은 결국 **비교할 수 없는 두 가지를 맞바꾸는
일**이라, 이 결정들은 성능 수치만으로는 정당화되지 않는다(이 문단은 이 사이트의 해석).

## 옮긴 뒤에 새로 생긴 것

축을 바꾸면 문제가 사라지는 것이 아니라 **다른 모양으로 다시 나타난다.** 다섯 사례 모두 그렇다.

- **LY** — 회전이라는 **운영 절차**가 생겼다. 회전 기간에는 생산자가 활성 공개키 전부로 DEK 를 각각
  감싸야 하고, 소비자는 자기 KEK ID 에 맞는 항목을 골라야 한다.
- **GitHub** — **이미지 빌드 파이프라인**이 새 시스템으로 생겼다. 캐시가 낡지 않게 하루에 여러 번
  돌아야 하므로 그 비용이 상시로 든다.
- **Dropbox** — 지연이 나빠진 것을 **다른 곳에서 감당**해야 한다. 회사는 그 악화가 전체 쓰기 지연의
  2% 라는 점을 근거로 삼는다.
- **Spotify** — 같은 파일이 **두 가지 일을 함께** 하게 됐다. 조회를 빠르게 할수록 배치 분석이
  나빠지므로, co-grouping·키당 한 페이지·컬럼 인터리빙을 **데이터마다 켜고 끄는 판단**이 생겼다.
- **Canva** — **읽고-고쳐-다시 쓰는 구조**가 생겨 수평 확장이 막혔다. 회사는 이것을 확장 가능하게
  만드는 대신 **배치로 묶어 "예상 가능한 요구를 넘어설" 만큼** 빠르게 만드는 쪽으로 우회했다.

## 각자가 감수한 것

- **LY** — **위험을 감수했다.** 공유 KEK 의 대가를 회사가 직접 적었다: **키가 새면 과거와 미래의
  메시지를 모두 복호화할 수 있다.** 완화는 KMS 인가와 주기적 회전뿐이고, **이 구조를 대체할 다른
  수는 글에 없다.**
- **GitHub** — **상시 비용을 감수했다.** 워크플로가 50분에서 12분이 된 대가로 이미지 빌드가 하루에
  여러 번 돌아야 한다.
- **Dropbox** — **지연 악화를 명시적으로 감수했다.** p95 디스크 쓰기 지연이 10~15% 나빠지고 읽기도
  나빠지는 것을 알고 뗐다. **이 사이트의 다섯 사례 중 잃는 것을 가장 분명하게 숫자로 밝힌 쪽이다.**
- **Spotify** — **레이아웃의 자유를 감수했다.** 사본을 만들지 않기로 하면 그 파일이 두 가지 일을
  해야 하고, 대가가 항목마다 붙는다(경계마다 약 20바이트, 단일 컬럼 스캔 I/O 몇 배).
- **Canva** — **즉시성과 수평 확장을 감수했다.** 폐기는 30분 창 안에서 반영되고, 한 청크는 한 번에
  한 워커만 갱신할 수 있다.

## 이 사이트에 아직 없는 것

- **축을 바꿨다가 되돌린 사례.** 다섯 다 **성공한 뒤에 쓰인 글**이라, 옮겼다가 더 나빠져 돌아온
  이야기는 어느 회사도 적지 않는다.
- **옮기기 전에 절충점을 얼마나 찾아봤는가.** 다섯 곳 모두 결과를 먼저 제시하고, **중간 지점을
  시도해 본 기록**은 GitHub(미리 만들어 둔 이미지를 써 봤다)과 Dropbox(캐시를 두고 있었다)에만
  간접적으로 있다.
- **잃는 쪽을 숫자로 밝힌 곳이 하나뿐이다.** Dropbox 만 악화 폭을 수치로 냈고, 나머지 넷은 대가를
  **말로만** 적는다 — LY 의 "키가 새면", Spotify 의 "프루닝을 내준다" 처럼.
- **한국 회사의 사례가 없다.** 이 축은 회사 규모나 나라와 무관해 보이는데, 이 사이트에 있는 한국
  회사들에서는 아직 같은 모양을 찾지 못했다.

## 읽는 사람에게

다섯 사례가 공통으로 말하는 것은 ***절충하지 말라*** 가 아니다. 다섯 곳 모두 무언가를 분명히
내줬고, 그중 셋은 회사 스스로 그 대가를 문서에 적었다.

말하는 것은 오히려 이쪽이다 — **손잡이가 잘 안 돌아갈 때, 손잡이를 더 세게 돌리는 대신 그것이
무엇에 달려 있는지 다시 볼 수 있다.** Canva 가 "부하를 어떻게 줄일까" 대신 ***이 부하는 무엇에
비례하는가*** 를 물은 것, Spotify 가 "읽기를 얼마나 빠르게 할까" 대신 ***읽기를 몇 번 할까*** 를
물은 것이 같은 종류의 되묻기다(이 문단은 이 사이트의 해석).

그리고 그렇게 옮긴 자리에서 문제는 **사라지지 않고 다른 모양으로 기다리고 있다** — 이미지 빌드
파이프라인으로, 키 회전 절차로, 레이아웃 판단으로. 다섯 사례가 정직한 것은 그 다음 모양까지
글에 적었다는 점이다.
