# 직접 만들 것인가, 가져올 것인가

> 비교 대상: Adyen `accounting-ledger`·`payment-path` · Cloudflare `unimog-edge-lb` ·
> Figma `livegraph-subscription` · LY `device-attestation` · 쿠팡 `seller-understanding` ·
> Spotify `podcast-previews`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> 안 하기로 한 결정들은 비교 문서 `안 하기로 한 것을 어떻게 적는가` 에, 다시 짓게 만든 것들은
> `무엇이 설계를 만료시키는가` 에 있다. 여기서는 **만들지 가져올지를 무엇이 갈랐는가**만 본다.

이 질문은 흔히 **"우리가 만들 수 있느냐"** 로 이야기된다. 그런데 일곱 사례에서 결정을 가른 것은
거의 그것이 아니었다.

## 무엇이 결정을 갈랐는가

| | 답 | 결정을 가른 것 |
|---|---|---|
| Adyen `accounting-ledger` | **만든다** (PostgreSQL + 자바) | **필요한 기능이 없었다** — **그때는 Kafka 가 exactly-once 전달을 지원하지 않았다** |
| Cloudflare `unimog-edge-lb` | **만든다** | **가져와도 쓸 부분이 거의 없었다** — l4drop 과 통합해야 했고, 핵심 C 코드가 **1,000줄 남짓**이라 만드는 비용 자체가 작았다 |
| Figma `livegraph-subscription` | **만든다** (LiveGraph) | **기성 시스템이 그 사용 방식을 권하지 않았다** — 대량 동시 구독. 게다가 협업이 제품의 본체라 이 계층이 경쟁력이라고 봤다 |
| Adyen `payment-path` | **가져온다** (CockroachDB) | 멱등성은 잘 정의된 문제였다 — **같은 회사가 정반대 결정을 내렸다** |
| 쿠팡 `seller-understanding` | **가져와서 고친다** | **시간과 연산** — 오픈소스 아키텍처에 도메인 데이터로 파인튜닝, CJK 성능을 보고 3B~20B 선호 |
| LY `device-attestation` | **표준을 따른다** (WebAuthn/FIDO2) | 만들지도 사지도 않는 세 번째 길 — **규격이 이미 있었다** |
| Spotify `podcast-previews` | **맡긴다** (관리형 Dataflow) | **운영 부담** — 직접 굴리면 **업데이트·확장·보안·신뢰성** 이 전부 우리 일이 된다 |

**일곱 중 어느 것도 "우리 팀이 그걸 만들 능력이 없어서"가 아니다**(이 문장은 이 사이트의 해석).
갈린 것은 **없는 기능 · 통합할 수 없는 코드 · 권장되지 않는 사용 방식 · 시간 · 표준의 존재 ·
운영 부담**이었다.

## 만든 쪽이 든 이유는 서로 다르다

세 회사가 만들기로 했는데 이유가 전혀 겹치지 않는다.

- **Adyen** — **기능의 부재.** 회계에서 같은 것이 두 번 처리되면 그것은 지연이 아니라 틀린 장부다
  (뒷문장은 이 사이트의 해석). exactly-once 가 없으면 그 후보는 후보가 아니다.
- **Cloudflare** — **통합 불가능성과 낮은 제작비.** Facebook 의 Katran 을 검토했지만 자사 l4drop 과
  묶어야 해서 **그대로 쓸 수 있는 부분이 거의 없었고**, 만들 것 자체가 **1,000줄 남짓**이었다.
  **남이 검증한 코드를 버리는** 대가를 치를 만했다.
- **Figma** — **사용 방식의 불일치.** Firebase·RethinkDB 같은 실시간 DB 도, Hasura·Prisma·PostGraphile
  같은 기성 GraphQL 계층도 **대량 동시 구독을 권하지 않는다.** 그리고 협업이 제품의 본체라
  이 계층이 경쟁력이 된다고 봤다.

**"만들기로 했다"는 같은 결론이지만, 재현할 수 있는 교훈은 셋 다 다르다**(이 문단은 이 사이트의 해석).

## 가져온 쪽도 공짜가 아니었다

| | 가져오고 받은 청구서 |
|---|---|
| Adyen `payment-path` | 기준이 **"핵심이냐 주변부냐"** 인데 **멱등성은 결제의 한복판인데도 가져왔다** — 기준이 규칙이 아니라 판단임을 보여 준다(**해석**) |
| 쿠팡 | **남의 아키텍처와 토크나이저에 얹힌다** — 한국어·중국어는 띄어쓰기와 문자 기반 특성, 큰 어휘 크기 때문에 **토크나이저가 곧 모델 품질**이 된다 |
| LY | 표준을 따라도 **안드로이드와 iOS 의 어테스테이션 객체 구조가 크게 달라 서버에 통일 로직이 여전히 필요하다**(회사가 직접 적은 한계) |
| Spotify | **버전에 묶인다** — Beam 을 2.35.0 에서 2.40.0 으로 올릴 때 전이 의존성 충돌(`grpcio` ↔ `google-cloud-pubsublite`)로 **"SDK harness disconnected"** 를 맞고 패키지를 손으로 걷어냈다 |

**가져오면 만드는 일이 사라지지만 다른 일이 생긴다** — 남의 릴리스 일정, 남의 토크나이저,
남의 플랫폼 차이, 그리고 기준 자체의 모호함.

## 같은 회사 안의 정반대 두 결정

Adyen 이 이 축에서 특이한 것은 **두 결정을 나란히 갖고 있기 때문**이다.

스트리밍은 **직접 만들었다** — 오픈소스에 원하는 기능 집합이 없었고, 특히 exactly-once 가 없었다.
그런데 멱등성은 **CockroachDB 를 가져왔다.** 회사가 밝힌 기준은 **핵심 흐름에는 자체 해법,
주변부(예: KYC 신원 확인)에는 오픈소스·벤더** 인데, **멱등성은 결제의 한복판이다.**

즉 이 기준은 **규칙처럼 보이지만 실제로는 판단**이다(이 문단은 이 사이트의 해석). 그리고 그렇게
직접 만든 것에는 시간이 지나 다른 문제가 붙었다 — **거절의 근거였던 사실이 사라진 것이다.**
회사는 결론 대신 질문을 공개했다: **이 틀이 20배를 더 갈 수 있을지, 아니면 Kafka 같은 오픈소스로
갈아야 할지 사내에서 논쟁 중이다.**

## 각자가 감수한 것

- **Adyen** — **두 방향의 대가를 동시에 졌다.** 직접 만든 쪽에서는 **토픽 같은 기능이 없다**는 것을
  알면서 골랐고 여러 차례 최적화가 필요했다. 가져온 쪽에서는 자기 기준의 경계가 흐려졌다(**해석**).
- **Cloudflare** — **검증된 코드를 버렸다.** 다만 만들 것이 1,000줄 남짓이라 그 대가가 작았다.
- **Figma** — **인프라 팀을 그 계층에 묶어 두기로 했다.** 기성 도구의 생태계도 못 쓴다. 협업이
  제품의 본체라는 판단으로 감수했다.
- **쿠팡** — **남의 토크나이저를 받아들였다.** CJK 에서는 그것이 곧 모델 품질인데도, 시간과 연산을
  아끼는 쪽을 골랐다.
- **LY** — **플랫폼 차이를 서버로 떠안았다.** 표준을 따랐는데도 두 OS 의 구조가 달라 통일 로직이 남는다.
- **Spotify** — **남의 버전에 묶였다.** 업데이트·확장·보안·신뢰성을 안 지는 대신, 업그레이드 한 번에
  의존성 지옥을 겪었다.

## 이 사이트에 아직 없는 것

- **가져왔다가 되돌린 사례.** 일곱 다 **한 방향으로 간 뒤에 쓰인 글**이고, 사 왔다가 결국 만들었거나
  만들었다가 사 온 이야기는 없다. Adyen 이 그 문턱에 있지만 **아직 결정하지 않았다.**
- **비용을 숫자로 낸 곳이 거의 없다.** Cloudflare 의 *1,000줄* 이 유일하게 구체적이고, 나머지는
  **직접 만들었을 때와 가져왔을 때의 비교 수치를 밝히지 않는다.**
- **"핵심이냐 주변부냐"를 실제로 어떻게 판정하는가.** Adyen 이 기준을 말로 밝힌 유일한 곳인데,
  자기 사례에서도 깔끔히 적용되지 않는다(**해석**). 다른 회사들은 기준 자체를 적지 않는다.
- **표준을 따르는 선택지가 한 번만 나온다.** LY 의 WebAuthn 뿐이다. 만들기·사기의 이분법 바깥이
  더 있을 텐데 이 사이트에는 아직 한 사례다.

## 읽는 사람에게

이 일곱이 함께 말하는 것은 **"직접 만들어라"도 "가져다 써라"도 아니다.** 세 곳은 만들었고 네 곳은
가져오거나 맡기거나 표준을 따랐다.

말하는 것은 이쪽이다 — **이 질문의 답은 대개 우리 쪽이 아니라 후보 쪽에 있다.** Kafka 에
exactly-once 가 없었는지, Katran 을 우리 l4drop 과 묶을 수 있는지, 기성 GraphQL 계층이 대량 동시
구독을 권하는지, 표준이 이미 있는지. **그러니 먼저 볼 곳은 우리 팀의 실력이 아니라 후보의 문서다**
(이 문단은 이 사이트의 해석).

그리고 **후보 쪽 사실은 변한다.** Kafka 는 지금 exactly-once 를 지원한다. 그런데 그때 만든 것은
아직 돌아가고 그 위에 최적화와 운영 지식이 쌓였다 — **바꿀 이유와 안 바꿀 이유가 같은 곳에서
자란다.** Adyen 이 결론 대신 질문을 공개한 자리가 정확히 거기다.
