# 무중단으로 갈아 끼우기 — 앱이 아는가 모르는가

> 비교 대상: Wix `read-first-then-write`(인프라 층)·`chatroom-by-chatroom`(앱 층) ·
> Cybozu `same-node-rolling`(애플리케이션이 딛는 바닥)
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> **되돌릴 수 없는 지점을 어디까지 미뤘는가**는 비교 문서 `되돌릴 수 있는 것을 먼저 한다` 에,
> **두 시스템을 나란히 돌릴 때 무엇을 정답으로 삼는가**는 `두 시스템을 나란히 돌려 옮기기` 에,
> **기계가 만든 것을 무엇이 통과시키는가**는 `문지기를 무엇으로 세우는가` 에 있다.
> 여기서는 **갈아 끼우는 동안 애플리케이션이 그 사실을 아는가 모르는가**, 그리고
> **무중단을 사려고 무엇을 내줬는가**만 본다.

멈추지 않고 옮긴 이야기는 대개 **무엇에서 무엇으로**로 전해진다. 그런데 세 사례에서 설계를
실제로 가른 것은 목적지가 아니라 **애플리케이션이 이관을 아는지 여부**였다. 그리고 그 답이
**같은 회사 안에서도 정반대로 갈렸다.**

가장 분명한 자리가 Wix 다. **인프라 팀은 요구사항에** *"Seamless for the application layer -
no code changes"* **를 넣고 프록시 뒤에서 갈아 끼웠는데, 제품 팀은 읽기마다** *"Checks if
migration of a chatroom has already ended"* **하게 만들었다.** **같은 회사, 같은 문제, 정반대
답이고 두 글은 서로를 언급하지 않는다**(이 대비는 이 사이트의 것).

## 앱이 아는가 모르는가

| | 무엇을 옮겼나 | 앱은 아는가 | 어디에 지식이 있나 |
|---|---|---|---|
| Wix `read-first-then-write` | 약 **200개 MySQL 클러스터** 사이 | **모른다** — *"no code changes"* | **ProxySQL** 이 읽기와 쓰기를 따로 돌린다 |
| Wix `chatroom-by-chatroom` | Cassandra → DynamoDB (메시지 **수 테라바이트**) | **전부 안다** | **챗룸별 이관 상태 표.** 읽기 경로에 들어가 있다 |
| Cybozu `same-node-rolling` | **20년 넘은 C++ CGI** 를 VM 에서 쿠버네티스로 | **모른다** | ⚠️ **대신 배포 구조가 앱의 가정에 맞춰진다** — 파일 잠금 때문에 파드가 한 노드에 모인다(이 정리는 이 사이트의 것) |

**⭐ Cybozu 가 가운데에 있다.** 앱은 아무것도 모르는데, **앱이 20년째 전제해 온 `fcntl` 잠금이
배포 방식을 정한다.** *"同じボリュームをマウントする複数の Pod 間で排他制御を機能させるには、
それらの Pod が同じ Kubernetes ノード上で動いている必要があります"* — **앱을 안 고치는 값을
인프라가 치른 셈이다**(이 해석은 이 사이트의 것).

## 무엇을 내주고 무중단을 샀는가

**셋 다 무언가를 내줬고, 내준 것이 다 다르다.**

| | 내준 것 | 그 자리의 말 |
|---|---|---|
| Wix `read-first-then-write` | **되돌릴 수 있는 구간** — 쓰기를 넘기는 순간 끝난다 | *"rollback is not an option without losing data, the 'new' data that has been committed only to the new cluster"* |
| Wix `read-first-then-write` | **데이터 고르기** — 파티션 수를 맨 앞에서 못 박는다 | *"cannot be changed safely mid-flight"* 이고 그래서 *"we do have data skew"* |
| Wix `chatroom-by-chatroom` | **자원과 지연** — 양쪽에 다 쓴다 | *"more resources from the application (heap, cpu, GC), keep that in mind"* · 쓰기 지연이 *"a bit"* 늘지만 *"definitely worth the rollback ability"* |
| Cybozu `same-node-rolling` | **분산** — 같은 볼륨을 쓰는 파드가 한 노드에 묶인다 | **가용성을 얻고 분산을 내줬다**(이 정리는 이 사이트의 것) |

**⭐ Wix 인프라 층 안에 정반대 성질의 결정이 둘 있다**(이 관찰은 이 사이트의 것). **트래픽은
되돌릴 수 있는 것부터** 옮기는데(읽기 먼저, 한 시간 뒤 쓰기), **파티션 수는 되돌릴 수 없는
것을 맨 앞에** 둔다. 그리고 **그 대가를 감추지 않고 적는다** — *"we do have data skew."*

## 되돌릴 길을 언제 닫는가

**이게 셋을 가장 크게 가르는 자리다.**

| | 되돌릴 길이 닫히는 때 | 그때까지 무엇을 유지하나 |
|---|---|---|
| Wix `read-first-then-write` | **쓰기를 넘기는 순간** | 읽기만 넘긴 **1시간 이상**의 *"real-traffic validation window"* |
| Wix `chatroom-by-chatroom` | **닫지 않는다** | *"Writes to Cassandra (the old data source) continued in parallel… the ability at any time to just go back to Cassandra"* |
| Cybozu `same-node-rolling` | ⚠️ **글에 롤백 이야기가 없다** | — (이 지적은 이 사이트의 것) |

**⭐ 같은 회사가 반대편 끝에 하나씩 있다**(이 대비는 이 사이트의 것). 인프라 층은 되돌릴 수
있는 구간을 **한 시간으로 못 박아 만들고 그 뒤로는 없앴고**, 앱 층은 **끝까지 열어 두는 값을
자원과 지연으로 냈다.**

## 버릴 것을 어떻게 골랐는가

**세 글 다 표준 답을 하나씩 버렸고 이유가 다 다르다.**

| | 버린 것 | 이유 |
|---|---|---|
| Wix 인프라 층 | **MySQL Dump** | *"it cannot be performed with zero downtime"* — **못 한다** |
| Wix 인프라 층 | **Amazon DMS** | *"DMS does not fully support this pattern. For our most critical MySQL workloads, it simply doesn't fit"* — **안 맞는다** |
| Wix 인프라 층 | **다중 소스 복제** | 프라이머리 노드 장애 위험과 번거로운 토폴로지 — **위험하다** |
| Wix 앱 층 | **클론을 떠서 옮기기** | **해 보고 버렸다** — *"our clone cluster had missing data and that not all data was transferred"* 이고 진행 상황도 *"completely blind"* |
| Cybozu | **StatefulSet** | *"更新時は古い Pod を削除してから新しい Pod を作成するため、リリースのたびにダウンタイムが発生する"* — **상태 있는 워크로드의 표준 답을 멈춤 때문에 버렸다** |

**⭐ 거절의 종류가 갈린다**(이 구분은 이 사이트의 것) — **못 한다 · 안 맞는다 · 위험하다 ·
해 봤더니 안 됐다 · 표준이지만 우리 조건에 안 맞는다.** 그리고 **실제로 해 보고 버린 기록은
Wix 앱 층 하나뿐이다.**

## 실패를 적은 쪽

**세 글 중 하나만 자기가 틀렸던 것을 적는다.**

- **Wix 앱 층** — 클론에 **데이터가 빠져 있었고** 진행 상황도 **안 보였다.** 그리고 그것이
  **개념 검증 단계(수 기가바이트)에서 잡혔다** — 본 데이터는 **수 테라바이트**였다.
- **Wix 인프라 층** — **실패도 되돌린 기록도 없다.** 대가는 셋 적지만 사고는 없다.
- **Cybozu** — 실패 기록은 없으나 **커널 동작을 직접 조사했다는 서술이 있다**
  (*"カーネルの挙動を調べました"*). **문서를 안 믿고 재 본 것이 이 글의 성격이다**(이 정리는
  이 사이트의 것).

## 옮긴 것이 맞는지 무엇으로 확인했는가

**여기서 셋이 다시 갈린다.**

| | 확인 방법 | 무엇까지 확인되나 |
|---|---|---|
| Wix `read-first-then-write` | **읽기만 넘긴 1시간 이상의 실트래픽 검증창** | 새 클러스터가 **진짜 트래픽을 견디는지.** 지연은 넘기는 시점에 *"near-zero seconds"* |
| Wix `chatroom-by-chatroom` | ⚠️ **대조 서술이 끝내 없다** | 대신 **불변성에 기댄다** — *"Luckily and importantly our messages are immutable"* |
| Cybozu `same-node-rolling` | **커널 실험** — `O_DIRECT`·타임스탬프 경계·파드 재시작 뒤 페이지 캐시(**5GB** 랜덤 데이터 → **977.2M** 캐시, 파드 상한 **1Gi**) | **옛 코드의 전제가 새 바닥에서도 성립하는지** |

**⭐ 확인의 대상이 다르다**(이 구분은 이 사이트의 것) — Wix 인프라 층은 **새 쪽이 견디는지**,
Cybozu 는 **옛 쪽의 가정이 유지되는지**, 그리고 **Wix 앱 층은 확인 대신 데이터의 성질에
기댔다.** 그 성질을 회사가 **운이라고 적는다.**

## 옮기는 양이 방법을 정한다

**두 곳이 "한 번에는 못 옮긴다"에서 출발한다.**

- **Wix 앱 층** — 메시지가 **수 테라바이트**라 클론 방식이 무너진 뒤 **챗룸 단위**로 쪼갰다.
  **새로 만든 챗룸은 비어 있으니 곧바로 완료로 표시**하고, 과거는 **한 달씩 거슬러** 올라간다.
  얻은 것이 *"The move was gradual. There was no one peak point where we moved production
  reads from one source to another."*
- **Cybozu** — 파일이 **수억 개**라 *"月 1 回の定期メンテナンスの時間内にすべてを転送すること
  はできません"*. 그래서 **미리 대부분을 보내 두고 점검 시간에는 차분만** 맞춘다 —
  **약 300만 파일이 15분.**

**⭐ 둘 다 창을 늘리는 대신 그 안에서 할 일을 줄였다**(이 정리는 이 사이트의 것).

## 이 사이트에 아직 없는 것

- **이관에 걸린 전체 기간이 셋 다 없다.** Wix 인프라 층은 **실제로 옮긴 클러스터 수**도,
  앱 층은 **옮긴 챗룸 수**도, Cybozu 는 **옮긴 테넌트 수**도 안 적는다. 규모(200개 클러스터 ·
  수 테라바이트 · 수억 파일)는 다 나오는데 **진도는 어디에도 없다.**
- **되돌린 기록이 하나도 없다.** Wix 앱 층은 *"at any time"* 되돌릴 수 있다고 하고 인프라 층은
  한 시간의 창을 만들어 두었는데, **그 길을 실제로 쓴 적이 있는지는 셋 다 안 적는다.**
  회사가 자기 블로그에 쓰는 글이라 당연할 수도 있다(**추정**).
- **한 노드에 묶인 대가가 실현된 기록이 없다.** Cybozu 는 같은 볼륨을 쓰는 파드를 한 노드에
  모으는데, **그 노드가 죽으면 그 테넌트가 통째로 죽는다**(이 지적은 이 사이트의 것).
  **그 위험을 어떻게 다루는지가 글에 없다.**
- **두 저장소가 정말 같은지 대조한 방법이 없다.** Wix 앱 층은 수명 기반 방식에서도
  *"one full data lifecycle"* 이 지나면 같아진다고만 하고 **확인 절차를 적지 않는다.**
- **쏠림의 크기가 없다.** Wix 인프라 층은 *"we do have data skew"* 라고 인정하지만
  **얼마나 심한지, 그래서 어떤 이관이 느려지는지는 안 적는다.**
