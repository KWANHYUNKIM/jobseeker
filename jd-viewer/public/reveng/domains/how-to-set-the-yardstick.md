# 자를 어떻게 세우는가 — 재기 전에 만들어야 하는 것

> 비교 대상: Snap `code-review-agent`·`agentic-code-search`·`mutual-gaze-align`·
> `spatial-benchmark` · Meituan `binarize-the-rubric`(그리고 같은 도메인의 LoHoSearch)
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
>
> **무엇을 좋다고 부를지**는 비교 문서 `무엇을 좋다고 부를 것인가` 에,
> **자가 틀렸음을 알아채는 이야기**는 `잘못된 자를 어떻게 알아채는가` 에,
> **재고 나서 무엇을 골랐나**는 `재 보고 나서` 에,
> **기계가 아예 판정할 수 없는 것**은 `기계가 판정할 수 없는 것을 어디에 두는가` 에 있다.
> 여기서는 **자를 만드는 일 자체**만 본다 — 참값을 어디서 구하고, 못 구하면 어떻게 적고,
> 자가 무뎌지면 무엇을 하는가.

무엇을 잘한다고 말하려면 자가 있어야 한다. 그런데 두 회사의 글 열 편 넘게에서
**자가 이미 있는 경우가 거의 없었다.** 자를 만드는 일이 매번 먼저 나오고, **그 만드는 방식이
여섯 갈래로 갈린다.**

가장 분명한 자리가 Snap 이다. **한 회사 안에서 네 가지 방식이 다 나온다** — 사람에게서 정답을
모으고, 참값을 못 구하면 못 잰다고 적고, 없는 자를 만들어 놓고 결과가 나쁘다고 적고,
**심지어 다른 글에서 앞 글의 범위를 좁힌다.**

## 자를 세우는 여섯 갈래

| | 방식 | 어디서 | 그 자리의 말 |
|---|---|---|---|
| ① | **사람에게서 정답을 모아 만들고 범위를 밝힌다** | Snap CodePal | Finding Lifecycle 의 좋아요·싫어요·병합·수정으로 골든셋을 만들고, 오탐 0% 가 *"the held-out golden dataset, **not on live traffic**"* 이라고 스스로 좁힌다 |
| ② | **참값을 못 구하면 못 잰다고 적는다** | Snap GNSS | *"Without a reliable, high-precision reference, we cannot provide definitive numerical accuracy metrics"* — 그래서 평가가 *"qualitative observations… rather than absolute error statistics"* 다 |
| ③ | **없는 자를 만들어 놓고 결과가 나쁘다고 적는다** | Snap 공간 벤치마크 | 추론을 더 시켜도 *"It mostly did not"* 이고 **16개 모델이 전부 틀린 문항이 둘** |
| ④ | **다른 편에서 앞 글의 범위를 좁힌다** | Snap Code Search | CodePal 의 '병합 전에 잡았다' 를 *"true only because reviews run on open PRs, **not because anything is build-verified**"* 로 좁힌다 |
| ⑤ | **자가 무뎌지면 새로 만든다** | Meituan LoHoSearch | 기존 기준이 포화되자 **지식 그래프에게 문제를 내게 했다**(위키백과 개체 **762만**, 간선 **2억 6,500만**). 난이도를 **검색 공간 크기**와 **구조 복잡도** 두 축으로 조절한다 |
| ⑥ | **애매한 기준을 이진화해 기계에게 맡긴다** | Meituan `binarize-the-rubric` | 예·아니오·모름으로 쪼개고 **일치율 85~90%** 를 넘겨야 기계 채점을 붙인다 |

**⭐ 앞 넷은 한 회사 안에 다 있고 뒤 둘은 다른 회사에 있다**(이 집계는 이 사이트의 것).
**그리고 갈리는 기준이 하나다 — 참값을 어디서 구할 수 있는가.**

## 참값을 어디서 구하는가 — 이것이 나머지를 정한다

| 참값의 출처 | 사례 | 그래서 어떻게 되나 |
|---|---|---|
| **사람의 판정** | Snap CodePal · Meituan 루브릭 | 자를 만들 수 있다. 대신 **사람끼리 먼저 맞춰야** 한다 |
| **서로 대조** | Snap EyeConnect | 두 기기의 관측을 맞대면 되므로 **2.6초·15cm·2.2cm** 같은 수치가 나온다 |
| **바깥에서 따로 구해야 함** | Snap GNSS | **못 구한다.** 지구 위 참값을 별도로 마련해야 하는데 없어서 **정성 서술로 남긴다** |
| **기계가 만들어 낸다** | Meituan LoHoSearch | 지식 그래프가 출제하고 **생성 → 자동 검사 → 사람 검토** 세 층으로 거른다 |

**⭐ Snap 의 수치 밀도 차이가 난이도가 아니라 여기서 온다**(이 정리는 이 사이트의 것).
EyeConnect 는 두 기기를 맞대면 되지만 GNSS 는 지구 위 참값을 따로 구해야 한다. **재는 일이
어려운 게 아니라 정답을 구할 수 있느냐가 갈랐다.**

## 기계에게 채점을 맡길 수 있는 조건

**Meituan 만 이 조건을 숫자로 못 박았다.**

- 애매한 지표를 **구체 차원으로 쪼개고**, 가능한 것은 **예·아니오·모름**의 이진 규칙으로 바꾼다.
- **사람끼리 일치율과 사람-기계 일치율이 85~90% 를 넘을 때까지** 규칙을 고친다.
- 효과가 수치로 있다 — **Beam 이 62%에서 92%로**, 数字站长은 **99%** 에 닿았다.
- **모름** 비율을 **루브릭 품질의 신호**로 쓴다.

**⭐ 이것이 '자를 만드는 일' 과 '기계에게 맡기는 일' 을 잇는 다리다**(이 정리는 이 사이트의 것)
— **확인 가능한 모양으로 바꾸기 전에는 기계가 채점할 수 없다.** ⚠️ **대가도 같은 방향이다** —
**이진화되는 것만 이진화되고, 안 되는 지표가 얼마인지는 적히지 않는다.**

**그리고 기준을 하나로 만드는 순서를 먼저 둔다** — 여럿의 합의 대신 **한 명의 중재자**를
세운다(*"1个'独裁者'好过10个'民主者'"*). ⚠️ **그 대가도 스스로 적는다** — 사용자층이 바뀌면
중재자의 판단이 현실과 어긋나는데 **그것을 감지할 방법이 없다고 미해결에 넣는다.**

## 점수는 모델의 성질이 아니라 자와 모델 사이의 관계다

**이 문서에서 가장 뚜렷한 숫자가 여기 있다.**

| 같은 모델 | 어느 자에서 | 점수 |
|---|---|---|
| GPT-5.5 | BrowseComp | **80% 이상** |
| GPT-5.5 | LoHoSearch(544문항) | **34.74%** |

**같은 모델이 자를 바꾸자 절반 아래로 떨어진다.** 맞힌 경우의 도구 호출도 **35회에서 61회로**
늘고, **그래프 구조(8.01%)가 트리 구조(11.89%)보다 어렵다** — 구조 복잡도가 독립적인 난이도
축이라는 것이 확인된다.

**⭐ 이것이 '자를 어떻게 세우는가' 가 왜 도메인인지 보여 준다**(이 정리는 이 사이트의 것).
**점수는 모델의 속성이 아니라 자와 모델 사이의 관계이고, 자를 바꾸면 순위가 아니라 결론이
바뀐다.**

**Snap 의 공간 벤치마크가 반대편에서 같은 것을 보인다** — **16개 모델이 전부 틀린 문항이 둘**
이면 그 문항은 **모델을 가르지 못하는 대신 모두의 천장을 보여 준다**(이 해석은 이 사이트의 것).

## 자를 만든 뒤 그 자의 한계를 적는가

**여기서 두 회사가 갈리고, 한 회사 안에서도 갈린다.**

| | 자기 자의 한계를 적었나 |
|---|---|
| Snap CodePal | ✅ **적는다** — 오탐 0% 가 골든셋 위의 값이지 실트래픽이 아니라고 스스로 좁힌다 |
| Snap GNSS | ✅ **적는다** — 애초에 절대 오차를 못 낸다고 밝히고 정성 서술로 간다 |
| Snap 공간 벤치마크 | ✅ **적는다** — 자기가 만든 자에서 결과가 나빴다고 적는다 |
| Meituan 평가 방법론 | ✅ **가장 많이 적는다** — **안 되는 방식 다섯 · 한계 다섯 · 미해결 다섯** |
| Meituan LoHoSearch | ❌ **한 줄도 없다** |
| Meituan VitaBench 2.0 | ❌ **한 줄도 없다** |

**⭐ Meituan 안에서 갈리는 선이 보인다**(이 대비는 이 사이트의 것) — **자를 논하는 글은
한계를 적고, 자를 내놓는 글은 안 적는다.** 회사 페이지에는 이것이 **'푸는 글' 과 '내놓는 글'
사이의 선**으로 정리돼 있다.

**⚠️ Snap 은 그 선이 없다** — 자를 만든 글(공간 벤치마크)도 자기 결과가 나빴다고 적는다.
**다만 Snap 쪽 자들은 대부분 사내용이고 Meituan 쪽은 공개 벤치마크다**(**추정** — 내놓는
자리가 다르면 적는 태도도 달라질 수 있다).

## 남이 만든 자를 좁히는 일

**Snap 에만 있는 방식이 하나 있다** — **다른 글에서 앞 글의 주장 범위를 좁힌다.**
Code Search 편이 CodePal 의 **병합 전에 잡았다**는 주장을 *"true only because reviews run on open
PRs, **not because anything is build-verified**"* 로 다시 적는다.

**⭐ 같은 회사의 다른 팀이 앞선 주장의 유효 범위를 공개적으로 줄인 셈이다**(이 정리는 이
사이트의 것). **이 사이트가 읽은 것 중 이런 자리는 여기 하나뿐이다.**

## 이 사이트에 아직 없는 것

- **자를 만드는 데 든 값이 없다.** Snap 의 골든셋을 몇 사람이 얼마나 걸려 만들었는지,
  Meituan 의 일치율 85~90% 를 넘기기까지 몇 바퀴를 돌았는지 **어느 글에도 없다.**
  유일하게 가까운 것이 Meituan 의 **지표가 20개에서 1년 뒤 200개로 자랐다**는 서술이다.
- **이진화가 안 되는 지표의 몫이 없다.** Meituan 은 **모름** 비율을 루브릭 품질의 신호로
  쓴다고만 하고 **그 값을 안 적는다.** **애초에 이진화할 수 없는 지표가 얼마인지도 없다.**
- **자를 바꾼 뒤 결정이 달라진 기록이 없다.** LoHoSearch 로 점수가 80%대에서 34.74% 로
  떨어졌는데, **그 결과로 무엇을 다르게 했는지**는 나오지 않는다.
- **자를 다시 잰 곳이 없다.** Meituan 의 일치율 문턱도 Snap 의 골든셋도 **처음 만든 뒤 다시
  검증했다는 서술이 없다.** 회사가 자기 블로그에 쓰는 글이라 당연할 수도 있다(**추정**).
- **못 잰다고 적은 뒤 어떻게 됐는지가 없다.** Snap GNSS 는 절대 오차를 못 낸다고 밝히는데,
  **그럼 그 시스템을 무엇으로 개선했는지**는 이어지지 않는다.
