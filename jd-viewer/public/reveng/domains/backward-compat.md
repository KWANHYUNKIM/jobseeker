# 옛 약속을 어떻게 지키는가

> 비교 대상: Netflix `per-title-encoding` · Stripe `api-surface`·`docdb-migrations` ·
> 토스 `payment-approval` · 쿠팡 `delivery-area`
> 각 회사 페이지에서 `확인`으로 정리한 사실만 엮었다. 비교에서 나오는 해석은 **추정**으로 표시했다.
> 토스와 Stripe 가 **API 를 어떻게 바꾸는지**(어댑터 대 생성 파이프라인)는 비교 문서
> `결제 — 되돌릴 수 없는 일을 다루는 세 가지 방식` 에 이미 있다. 이 문서는 방식이 아니라
> **그 약속의 비용이 어디에 나타나는가**를 본다.

옛 약속을 지키는 이야기는 대개 API 버저닝 이야기로 흐른다. 그런데 Netflix 를 옆에 놓으면
그게 API 만의 문제가 아니라는 게 드러난다.

> 스트림이 **이전에 인증된 모든 Netflix 기기에서 재생되어야 한다.**

그래서 이 회사는 해상도를 여섯 가지로, 비트레이트를 유한 집합으로 묶어 두고, **convex hull
위가 파레토 효율이라는 것을 알면서도 그 위에 정확히 앉지 못한다.** 계약서가 아니라
**이미 팔려 나간 물건**이 오늘의 인코딩 선택지를 정한다.

## 비용이 어디에 나타나는가

| | Netflix `per-title-encoding` | Stripe `api-surface` | 토스 `payment-approval` |
|---|---|---|---|
| 무엇에 대한 약속인가 | 재생 가능성 — 스트림이 열려야 한다 | API 계약 | API 계약 |
| 약속의 상대 | **팔려 나간 기기** | 연동한 개발자 | 연동한 가맹점 |
| 지키는 방식 | **선택지를 유한 집합으로 묶는다** | 릴리스마다 **OpenAPI 스냅샷을 그 버전의 정식 설명으로 저장** | 버전을 경로 최상단에 두고 **완전 독립** |
| 비용이 나타나는 곳 | **오늘의 최적점** — hull 위에 못 앉는다 | **과거를 되살릴 능력** | **끝나지 않는 유지비** |
| 구체적으로 | 기기별 래더를 따로 만들면 **저장 효율이 떨어진다** | **v1 은 과거 버전의 설명을 다시 만들 수 없다** — 새 변형·메타데이터를 역채우기 못 한다 | 버전 수만큼 검증·응답 코드가 병존해 **선형으로 증가** |
| 언제 끝나는가 | **알 수 없다** — 기기가 사라져야 끝난다 | v2 는 모든 변경이 디스크에 남아 역사 전체를 재현할 수 있다 | **오래된 버전이 언제 죽는지 아무도 모르게 된다** |

세 곳 모두 약속을 지키는데, **깎여 나가는 것이 서로 다른 종류다.** Netflix 는 지금 만들 수
있는 것의 상한을 깎이고, Stripe 는 과거를 다시 설명할 능력을 깎이고, 토스는 시간을 깎인다.

## Netflix — 약속의 상대가 사람이 아닐 때

이 사례가 특별한 이유는 **상대에게 알릴 방법이 없다**는 데 있다.

API 라면 버전을 붙이고 마이그레이션 안내를 낼 수 있다. 그런데 5년 전에 팔린 TV 는 버전을
읽지도 않고, 회사가 그 기기의 지원을 끝내면 그건 호환성 문제가 아니라 **그 회원에게는 서비스가
사라지는 일**이 된다.

그래서 이 약속은 인코딩의 아주 안쪽까지 들어온다.

- 해상도는 1920×1080 · 1280×720 · 720×480 · 512×384 · 384×288 · 320×240 여섯 가지, 비트레이트도
  유한 집합이며 인접 값의 증분은 약 5%다.
- **이유가 성능이 아니라 하위 호환성이다.**
- 그리고 그 제약이 최적화를 뒤집기도 한다 — 1080p 까지 덮는 래더 하나만 두면 **720p 상한
  태블릿은 대역폭이 남아도 그 아래 스트림에 갇힌다.** 그래서 480p·720p 상한 기기용 래더를
  따로 설계하는데, 그러면 인코드가 늘어 **타이틀의 저장 효율이 떨어진다.**

**하위 호환을 지키는 비용이 저장 비용으로 옮겨 앉는 셈이다**(이 문장은 이 사이트의 해석).

## Stripe — 지금 잘 만드는 것과 과거를 되살리는 것은 다른 문제

Stripe 는 계약을 붙들어 두는 쪽으로 아주 멀리 갔다. 새 API 버전을 낼 때마다 **당시의
OpenAPI 스펙을 그 버전의 정식 설명으로 저장**하고, PR 병합 전 자동 테스트가 명명·필드 타입·
역호환성을 검사하며, **v2 는 과거 버전에 대한 변경까지 감지**한다.

그런데도 회사 페이지에 남은 불변식은 이것이다.

> 지금 잘 만드는 것과 과거를 되살리는 것은 다른 문제다.

v2 는 Protocol Buffer 기반 DSL 로 정의해 **모든 변경이 디스크에 남아 역사 전체를 재현할 수
있는데**, v1 은 역사적 아키텍처 때문에 그게 안 된다. 새 변형이나 메타데이터를 옛 버전의
설명에 역채우기 할 수 없다.

**앞으로의 호환성은 설계로 살 수 있지만, 이미 지나간 시간은 살 수 없다**(마지막 문장은 이
사이트의 해석).

## 토스 — 끝을 정하지 않는 대가

토스의 불변식은 가장 단호하다.

> 가맹점이 이미 연동한 버전의 계약은 나중 버전이 무엇을 하든 그대로 지켜진다.

그래서 버전을 경로 최상단에 두고 각 버전을 완전히 독립된 API 로 관리하고, 가맹점이 보내는
수백 개의 평평한 파라미터는 Converter 가 흡수해 도메인 객체로 바꾼다 — **비즈니스 로직은
어느 시대의 파라미터로 들어왔는지를 몰라도 된다.**

대가는 회사 페이지에 그대로 적혀 있다. 유지 비용이 **버전 수만큼 선형으로 늘고**, **오래된
버전이 언제 죽는지 아무도 모르게 된다.**

## 바꾸는 동안에는 무엇으로 지키나

여기가 이 비교에서 가장 실무적인 부분이다. 셋 다 **돌아갈 길을 먼저 깔고** 옮겼는데,
**되돌리는 단위가 서로 다르다.**

| | 토스 `payment-approval` | Stripe `docdb-migrations` | 쿠팡 `delivery-area` |
|---|---|---|---|
| 무엇을 옮기나 | 10년 된 결제창 → 새 결제창 | 살아 있는 금융 데이터의 샤드 | 우편번호 기반 → H3 기반 배송 영역 |
| 전환 방식 | 신규·레거시 **병행 운영** + 가맹점별·기능별 카나리 | **versioned gating** — 프록시가 버전 토큰을 붙이고, 샤드는 자기가 아는 것보다 새 토큰만 받는다(MongoDB 커스텀 패치) | 새 시스템이 **레거시와 함께 쓰일 수 있게** 둔다 |
| 되돌리는 단위 | **가맹점 하나** | **샤드 하나** — 양방향 복제로 원본 복귀 가능 | 되돌리지 않고 **공존** |
| 판정 기준 | PREPARE 대비 CONFIRM 비율이 정상 범위를 벗어나면 **자동 원복** | 핵심 단계를 **계획된 primary failover 보다 짧게**(실제 2초 미만) | (자료에 없음) |
| 감수한 것 | 두 시스템 동시 유지 · '정상 범위' 판정 체계를 먼저 만들어야 함 | MongoDB 패치 · 토큰 번호가 또 하나의 상태 | 두 체계를 동시에 유지하는 비용 |

Stripe 의 정의가 이 절의 핵심이다. **'멈추지 않는다'를 절대적 목표가 아니라 애플리케이션의
재시도 예산으로 정의**했다 — 중단이 재시도 예산 안에 들어오면 무중단이다. 그래서 전체가
2초 미만에 끝나고 실패한 요청은 재시도로 성공한다.

그리고 쿠팡은 되돌리는 장치가 아니라 **아예 공존**을 골랐다. 이유는 단순하다 — **매일 물건이
나가는 시스템이라 한 번에 갈아엎을 수 없다**(뒷부분은 쿠팡 페이지에서도 추정으로 적혀 있다).

## 약속의 상대가 끝을 정한다 (추정)

세 회사를 나란히 놓으면 **끝낼 수 있는지가 방식이 아니라 상대에 달렸다**는 게 보인다.
이 묶음은 이 사이트의 해석이다.

- **연동한 개발자**가 상대면 버전이라는 이름을 붙일 수 있고 원리상 알릴 수 있다. 그런데
  토스의 경우 실제로는 **언제 죽는지 아무도 모르게 됐다** — 알릴 수 있다는 것과 끝낸다는 것은
  다른 일이다.
- **팔려 나간 기기**가 상대면 알릴 방법이 없다. Netflix 는 끝을 정하는 대신 **선택지를 좁혀
  안고 간다.**
- **매일 나가는 물건**이 상대면 멈출 수 없다는 것 자체가 제약이 된다(쿠팡).

## 이 사이트에 아직 없는 것

- Netflix — 지원 기기의 인증 기준이 무엇인지, 어떤 기기가 언제 지원 목록에서 빠지는지
- Stripe — 오래된 API 버전의 실제 지원 기간, v1 의 '역사적 아키텍처'가 구체적으로 무엇인지
- 토스 — 실제로 살아 있는 API 버전이 몇 개인지, 버전 폐기 정책이 있는지
- 쿠팡 — 레거시와 새 배송 영역 체계를 언제까지 함께 둘 계획인지

**네 회사 모두 '옛 것을 언제 끄는가'에 대한 답이 비어 있다.** 하위 호환을 다루는 시스템을
읽을 때는 이 질문을 먼저 던지고, 답이 없다는 사실 자체를 기록해 두는 편이 낫다.

## 읽는 사람에게

하위 호환은 대개 '옛 코드를 어떻게 계속 굴릴까'의 문제로 다뤄진다. 그런데 이 네 사례에서
실제로 값을 치른 곳은 전부 다른 자리였다 — **오늘 만들 수 있는 것의 상한(Netflix), 과거를
다시 설명할 능력(Stripe), 끝나지 않는 유지비(토스), 갈아엎을 수 없다는 사실(쿠팡).**

그러니 새 시스템을 설계할 때 물어야 할 것은 '어떻게 호환할까'보다 앞에 있다 — **이 약속의
상대가 누구이고, 그 상대에게 끝을 알릴 방법이 있는가.** 알릴 방법이 없다면 그 약속은
설계 제약이 아니라 **영구적인 상수**로 잡아야 한다.
